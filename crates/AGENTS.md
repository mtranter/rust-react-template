# Backend (`crates/`)

Rules for the Rust backend, a modular monolith: each module is a crate that owns its schema and could be lifted out into its own service (ADR 0001). The repo-wide rules are in the root `AGENTS.md`. Paths are from the repo root.

**Copy the reference code.** This file holds what the code can't show you: the rules, the reasons, and what isn't built yet.

The platform's own modules are in `crates/platform/` (today `access`, ADR 0040): registered with the server like the app's in `crates/modules/`, kept registered by `make init`, and pulled with the platform's later changes (`TEMPLATE_VERSION`), so an app never edits them. The reference modules are in `crates/reference/`, and the journeys over them in `crates/reference/journeys/`: compiled, linted and tested, and registered with the server in the template only (`make init` registers them with no server, until an app's own code shows the same). Below, `notes` is `crates/reference/notes/core` and `notes_api` its `api`, and so on.

| Doing | Copy |
|---|---|

| Providing a `<module>-api` crate, a port with an adapter | `crates/reference/users` (`users_api`, `Mailer` in `mail/`) |

## Commands

- `make new-module NAME=<module> [ENTITY=<aggregate>]` scaffolds and registers a write module, with a projection of its own topic to keep, repoint or delete (see "Adding a module").
- `make prepare` after changing any `query!` (refreshes the checked-in `.sqlx`; needs a migrated DB). `make migrate`, `make seed`, `make check-sql`, `make check-deps`, `make check-modules`, `make check-spec`, `make db-up|db-wait|db-down`, `make db-reset` (deletes the dev database's volume, then migrates and seeds); the rest: `make help`.
- One test: `make db-wait`, then `SQLX_OFFLINE=true DATABASE_URL=postgres://app:app@localhost:5432/postgres cargo test -p widgets creating::` (any substring of the test path). The database is `postgres`, never `app` (tests create theirs beside it); without `SQLX_OFFLINE=true`, `query!` fails with `relation "widgets.widget" does not exist`.
- Rust CLI tools are repo-local, run as `cargo bin <tool>` (`cargo bin cargo-deny check`), never a global `cargo deny`/`sqlx`. To bump one, edit `[workspace.metadata.bin]` in the root `Cargo.toml` with a range qualifier (`^0.20`) and re-run `make setup`.
- For Rust symbols (callers, implementations, a type) prefer the LSP tool to grep: grep misses re-exports and trait impls. Grep for strings and non-Rust files.

Gotchas:
- A test panicking `connect to DATABASE_URL`: Postgres is down (`make db-up`).
- Two test runs against one Postgres at once (two worktrees, cargo-watch beside `make test`) collide: template and per-test database names derive from the template name and test path.
- A failing test keeps its `_test_*` database to inspect until it next runs; renamed tests leave theirs behind: `make test-db-clean`.

## Architecture

`make check` enforces the module graph, schema isolation, registration and per-crate clippy bans (ADR 0017). Everything below it can't see. Breaking these defeats the template's purpose.

### Layers (ADR 0007)

Each module is a crate (`crates/modules/<module>/core`, package `<module>`; the platform's are in `crates/platform/<module>/core`, the reference modules' in `crates/reference/<module>/core`) with layer folders `web/`, `application/`, `domain/`, `db/`, each re-exported from its `mod.rs` (`crate::domain::User`, never `crate::domain::user::User`). **Dependencies point inward**: `web → application → domain`, `db → application`; a use case flows handler → service → repository. Grow a layer by adding files by concern, not by growing one file.

- **`web/` translates and holds no logic.** `#[OpenApi]` on a **unit struct** `XEndpoints` taking its service as `Data<&XService>`, never struct state, so `dump-spec` builds the spec with no database (ADR 0006). Request → command → service → HTTP. Every operation returns `app_web::ApiResult<T>`, so every one declares the shared `ErrorBody` error responses; `?` converts an `AppError`.
- **`application/` owns the unit of work.** `XService` holds `Arc<dyn XRepository>` (a trait object, not a generic), `Arc<dyn EventPublisher>`, `Arc<dyn Transactions>` and `Arc<dyn Clock>`. One method per use case: load → domain action → save and publish in a unit of work (`begin` … `commit`). It mints ids, reads `self.clock.now()` (never ambient time, ADR 0020), and owns cross-aggregate rules. The repository trait lives here: `get → Option<Versioned<X>>`, `save(&mut Tx, &X, Expected) → Version`, `list(&ListQuery<XSortKey>, &Rows) → Listed<Versioned<X>>`; reads run on the pool, writes take the `Tx`. `error.rs` maps the domain error onto `AppError` exhaustively, pinning it to the input at fault with `AppError::invalid_field(path, msg)` where it can (`path` as the client names it, `authorId`).
- **`domain/` is pure and synchronous**: no repositories, no async, no `Utc::now()`, no `XId::new()`, never `poem`/`sqlx`. Constructors take the id and `now`, so the same constructors build fresh aggregates and seeds; `restore(..)` rebuilds persisted state.
- **`db/` holds the only raw SQL**; a write runs on `app_db::conn(tx)`. `save` is an INSERT (`Expected::New`) or a version-guarded UPDATE (`Expected::Version`), never an upsert. Map a constraint violation by its name with `app_db::map_db_error` (copy `crates/reference/users`); anything else is `AppError::internal`. A crate with `migrations/` needs `build.rs` (`cargo:rerun-if-changed=migrations`), or Cargo reuses a build lacking the new one.
- **`di.rs`** builds the service in a `provider(ctx, ..)` from the shared `app_module::Context` (pool + clock), its worker handlers in a `handlers(ctx, ..)`, and bundles them with the migrations and seed in `module(..) -> app_module::Module` (ADR 0019). `lib.rs` exports only the `Endpoints`, public domain types, migrations, `di.rs` constructors, the ports a driver fakes, its resources' `Columns` (for the agreement test), and `pub mod seed` under the `seed` feature (none of the last four for a module that owns no data).
- An external system other than the database is a port in `application/`, with its adapter in a folder named for it (`crates/reference/users/core/src/mail/`).
- `#![allow(clippy::disallowed_types)]` only in `db/mod.rs`, `di.rs`, `seed.rs` and test `main.rs`, never under `application/` or `domain/`.

### Aggregates and versions (ADR 0016, 0030)

- **An aggregate is a consistency boundary**, drawn around the rules that must hold in one transaction, not around tables or modules. An entity is a **child** when its root's rules span it, it can't outlive the root, and there are few enough per root to load them all (a Note's Items: unique text, at most 50); otherwise it is a root, referred to by id. Only a root has a repository, a service and a topic. A module may own several roots.
- **A use case saves exactly one root** and may read others to validate. A consequence for another root is a subscriber to the first root's event; a subscriber may change several roots in one delivery, each saved and announced as its own change.
- **The root's version is the aggregate's only one.** It lives in `app_persistence::Versioned`, never in the aggregate. Every write, a child's included, saves the root with its version guard: commit order per key, and so event order, depends on it. A child's operations take and answer with the root's `ETag` (`crates/reference/notes`' `/notes/:id/items`), so any change makes every client's copy stale. That is deliberate: a version per child was rejected (ADR 0030).
- Single-resource responses are `app_web::WithETag<XResponse>`, with `version: string` mirrored in the body. The expected version comes only from `If-Match` via `app_web::if_match_version` (absent → 428, stale → 412), never the body. A lost race is stale, never retried. In `db/`, a child's rows are rewritten beside the root's row in the same `Tx`, after its guard passes (`crates/reference/notes/core/src/db/items.rs`).

### Events and subscribers (ADR 0011–0015)

Built on Kafka's model: a topic per root, keyed by the root's id, ordered per key by its version, with a subscription as a consumer group, hand-rolled on a Postgres outbox.

- **Every state change publishes one event per root, in the unit of work that saves it**, so it goes out if and only if the write commits: each use case that saves a root calls `self.publisher.publish(&mut tx, events::pending(&x, version, event))` with the `Tx` it saved in. Never call an external system or another module after `commit`: anything else that must follow a write (mail, another module's reaction) is a subscriber.
- **The domain decides what happened**: each transition returns a variant of the aggregate's plain `#[must_use]` `XEvent` in `domain/` (constructors `(Self, XEvent)`, mutations `XEvent`, `Option<XEvent>` where they may change nothing, deletion `x.delete() -> XEvent`), a past-tense fact, never a command in disguise (`UserRegistered`, not `SendWelcomeEmail`). `application/events.rs` maps it exhaustively to the topic's enum, the one place domain names meet the wire.
- **Each root has a topic**, declared with `app_events::topic!` in the `-api`'s `events::v1` (copy `crates/reference/notes/api/src/events.rs`): name (`notes.note.v1`), `source`, `retention`, entity, key, one line per event (`NoteDeleted => Deleted: "notes.note_deleted"`, `NoteItemAdded => ItemAdded(OfItem): ".."` for one with a context). Its event enum is deliberately exhaustive, not `#[non_exhaustive]`: a new event breaks every whole-topic consumer in the same change. Events and the entity only gain fields, each `#[serde(default)]`; removing an event or changing the entity incompatibly is a new topic (`notes.note.v2`) published beside the old. Its module declares it publishes it (`Module::new(..).publishes::<NoteTopic>()` in `di.rs`), so `migrate` registers it.
- **The outbox is a compacted log** (ADR 0033). Each topic declares its `retention:` in `topic!`, with no default, and `migrate` registers it in `messaging.topic`; an unregistered topic is never compacted. Compaction (`Worker::compact`) deletes a relayed event once it is older than its topic's retention, a later version of its key exists and no unfinished backfill has yet to copy it: every key's latest event stays forever, a deletion's included, and jobs are copies it never touches. So a consumer can't rely on the outbox for history older than the retention.
- **An event's payload is `EventPayload { entity, context }`.**
  - **`entity` is the root's latest state** (event-carried state transfer), so subscribers never call back; a deletion carries the state as it was last. The entity is an API, not a copy of the aggregate: its type lives in the `-api`'s `events::v1`, apart from any published view record, built in `application/events.rs`. Usually that is every property but the audit ones; leave out what consumers shouldn't depend on or see, and reshape a field where the domain's own form would leak (a secret, an internal code). Each published field is coupling you must keep.
  - **`context` says what changed where the state can't.** An event about a child names it: `NoteItemRemoved` carries the Note as its entity and `OfItem { item_id }` as its context, since from the latest state alone a consumer can't tell which item went. Use none where the entity says it all (`NoteCreated`).
  - It carries the root's new version: `PendingEvent::on::<XTopic>(version, &state, event)` takes the `Version` `save` returned, or for a deletion the one removed `.next()`, so it is the newest of its key.
- **Subscribers are idempotent.** A subscriber implements `app_persistence::Handle<E>` for one event (receiving `EnvelopeOf<E>`) or `Handle<XTopic>` for a whole topic (matching its `event` with no wildcard arm) in its `application/`, registered in its `handlers(..)` under a stable queue name (`Handlers::new().on::<UserDeleted>("notes.archive_deleted_authors_notes", service)` in `crates/reference/notes`). Handlers run in the worker inside their own `Tx`, at least once, in order per key within each queue, with no order across keys, topics or queues, and gaps where a subscription is filtered or newer than the key. A failing one backs off and holds up only its key, then is dead-lettered in `messaging.job`, as is one whose worker dies on every attempt. A copy of another module's state is a projection (ADR 0036): `Handlers::new().project::<NoteTopic>(queue, rows)` (`app_db::Projecting`), with `rows` implementing `app_db::Project` in `db/`. The framework applies an event only when it is newer than the copy, since a rerun dead letter arrives out of order, and keeps a tombstone for a removed key in `messaging.projection_version`, so `put` is a plain upsert and `remove` a plain delete, with no version column. Reactions to facts (mail, archiving) don't compare versions.
- **Subscriptions are rows in `messaging.subscription`, registered by `migrate`**, never on worker start, so old and new builds relay alike during a rolling deploy (ADR 0014). A queue is bound to one topic forever and a retired name is never reused. Retire one with a migration, never by just deleting its handler. `messaging.retire` stops relaying to the queue, completes its unfinished backfill and dead-letters what it hadn't run, serialised against the relay and any backfill chunk in flight, so neither adds a live job to the queue after it:

  ```sql
  SELECT messaging.retire('<queue>');
  -- and for a projection's queue, in a later migration once nothing serves its tables:
  DELETE FROM messaging.projection_version WHERE queue = '<queue>';
  ```
- **A subscription starts from `latest`** (`Handlers::on`): it receives the events relayed after `migrate` first registers it. **A copy of state starts from `earliest`** (`Handlers::on_from_earliest`), subscribing to the whole topic and comparing versions: it is backfilled once with every event its topic's outbox held when `migrate` first registered it (after compaction, each key's latest plus the history within the retention): `migrate` only records the backfill in `messaging.backfill` (complete at once when no event of its type has been relayed), and workers copy it into the queue a chunk at a time, alongside the relay (ADR 0035). Until it has caught up (`app_db::caught_up`: every event its topic held at registration, relayed then or not, delivered and handled, judged by outbox `seq`), a copy built from it is incomplete, so a read module serves it only through `app_db::Generations`, which answers `unavailable` (503) until then (ADR 0036). A key's live events wait for its backfilled ones, but other keys' don't, so it can't assume it has seen all history before its first live event. A reaction to facts starts from `latest`, or it would re-run for history. A start is fixed once registered: changing it in code only makes `migrate` warn.
- **There are no jobs or scheduled work** (ADR 0015). Don't add them until a module needs "do X at time T". Compaction is no exception: it is the worker's own maintenance of the log, not module work. Each worker compacts after its first poll, then after its first poll once `APP_OUTBOX_COMPACT_EVERY` has passed by its clock (`Worker::compact_if_due`), uncoordinated: N replicas compact up to N times a period, which the database alone makes safe, so add no lock, lease or schedule table.
- **Broadcasts between instances go over the bus** (ADR 0039), never the outbox, whose queues each deliver a job to one worker. A module that publishes or follows a channel builds a `app_bus::Channel<T>` from `ctx.bus()` (its name prefixed by the module: `notes_changes`), with a `Hub<T>` where the instance holds the clients (an SSE stream, a WebSocket), and registers as `Module::new(..).broadcasts()`, which makes the server and worker refuse to start without `APP_REDIS_URL`. The bus loses messages: keep the truth in the database and treat `Received::Gap` as the cue to recheck it. `T` changes only compatibly, as an event does. Tests start their Valkey with `app_bus::testing::Valkey` (the bus crate's `test` feature) and pass `ctx.with_bus(Arc::new(valkey.bus().await))`; nothing else touches Redis.

### Lists (ADR 0018)

Take `ListQuery<XSortKey>` and the caller's `app_authz::Rows`, and return `Listed<T>`; build the SQL with `QueryBuilder` + `app_db::push_scope` + `app_db::push_list_clauses` (the one sanctioned runtime SQL, since `query!` can't vary `ORDER BY` or a policy's `WHERE`), ending in a unique tiebreak. The total's `COUNT(*)` takes the same `push_scope`, so pages and totals count only what the caller may see. **Never filter rows after the query**: paging and totals would count rows the caller can't see. The handler takes separate `limit`/`offset`/`sort` params and returns `ListResult<XResponse>`. Copy `crates/reference/notes`.

### Across modules (ADR 0002, 0008–0010)

- **Choose the mechanism by why the data is needed, not how much** (ADR 0009, 0038). Take the first that fits:
  1. **To decide or validate**: call the provider's `<module>-api` trait, at any size (a bulk need gets a batch method like `users_exist(ids)`).
  2. **To show** another module's columns beside a page of your own (an author's name by `created_by`), never sorting, filtering, searching or paging by them: **enrichment**. Read the page from your own tables, then make one batch call to the provider's `-api` for just that page's ids (`display_names(ids)`), tolerating ids it no longer has. Never per row, never a whole table.
  3. **To list, search, filter, sort or page by** another module's columns: a **projection** of the provider's topic, copying only the columns the read uses, **in the module whose feature owns the screen**, even when other modules keep their own copy of the same topic.
  4. **For a read no one module owns** (a search across several modules' roots): a read module.

  A write module never reads views or joins across schemas.
- **Optimise for one feature in one module.** A feature's change, its screen's projection included, stays in its own crate, so parallel agents never edit the same files and each needs only its module and its providers' `-api` crates in context. So: duplicate copies rather than share one (no shared user copy, no projection crate other modules read); don't move a screen to a read module to save a copy; and keep each module's own `web/`, with no backend-for-frontend over modules: it would be a crate every feature edits, it can't sort by another module's columns at request time, and it invites one request into several modules' commands.
- **Modules meet only through pure `<module>-api` crates** (no poem/sqlx), never a core crate. Ids cross as plain `Uuid`; each side keeps its own typed ids and converts in `application/`. The provider implements the trait in `application/` and exposes a constructor from `di.rs`; `server` passes it to the consumer's `module(..)`. Never write another module's data, through its `-api` or otherwise: publish, and let the owner react.
- **No foreign keys between modules**: a cross-module id is a plain `uuid` column, validated on write through the provider's trait where the rules need it; consumers tolerate it dangling. A foreign key would couple migration order, deletes and locks, and stop a module being lifted out.
- **Projections** (ADR 0036) are tables in a module's own schema, filled by `earliest` projections of topics, so the module needs nothing of a provider but its events and could outlive the provider being lifted out. Any module may keep one: of another module's topic to list or search by its columns, or of its own topic for a read shape its aggregate's tables can't serve well (the module template's `widget_search`), accepting that its own writes show there only once the worker delivers them; keep every other read on the aggregate's tables, and delete the template's copy when nothing needs it. An `XFinder` (or search) trait returns read models from it. **Read modules** (ADR 0010, 0036) are modules whose only data is projections, for a read no one module owns: they have no `domain/`. Shape the tables for the queries (denormalise, index), and take every column from the events' entities: if one is missing, the provider's entity gains it (`#[serde(default)]`, so the projection tolerates its absence in older events). The finder serves the newest generation of tables that has caught up (`Generations`); a new shape is a new generation, new tables and `_v2` queues listed first, switched to once caught up, the old one retired later. A read module depends on providers' `-api` crates for their topics, never calls `-api` traits, has no seed, and its driver publishes the providers' events itself.
- **Published views** (`users_api.user_v1` in `crates/reference/users`, from the provider's own migrations in its `<schema>_api` schema) remain for SQL that must read another module's data now, declared in `[package.metadata.module] reads` (`make check-sql` enforces it); no module reads one today. A view only gains columns, a breaking change ships as `_v2` beside `_v1`. Each has a **published record** in the provider's `-api` (`users_api::v1::User`), `#[non_exhaustive]`, gaining a field when the view gains a column, never returned from a trait; seeds describe themselves to other modules with them.
- **Isolation** is enforced three ways (ADR 0017); keep all passing: the Cargo graph (`make check-deps`: no core depends on another core, an `-api` depends only on pure crates, a write module declares no `reads`); `deny.toml` (every module core, read modules included, in both the `sqlx` and `poem` `wrappers` lists, never an `-api`); a per-crate `clippy.toml` (copy a sibling's) under `-D warnings`.

### Common crates (ADR 0003)

Split pure (`app-authz`, `app-domain`, `app-error`, `app-events`, `app-persistence`, `app-test-support`) from framework-coupled (`app-web` = poem, `app-db` = sqlx, `app-module` = both, for `di.rs` and the server; `app-test-db` = sqlx, tests only; `app-fake-oidc` = poem, the OIDC provider `make e2e` signs in through, never a dependency of shipped code). Never merge them, and never add poem/sqlx to a pure crate (`make check-deps` fails a pure crate depending on any non-pure workspace crate). Declare ids with `app_domain::uuid_newtype!`. Config and the logging and trace pipeline live in `crates/server`, not `common`; only the request's span, the query spans (`app_web::QuerySpans`) and the metrics measured where requests are served (`app_web::PoolWaits`, and the pool's in `app_db::observe_pool`) are `app_web`'s and `app_db`'s.

### API surface

- **One error shape** (ADR 0022): every failure is an `ErrorBody` (`code`, `message`, optional `fields: [{path, message}]`, `requestId`, and `traceId`, the request's W3C trace id, whenever a trace is recorded). Handlers return `ApiError`, and `render_error` (applied with `catch_all_error`) renders framework failures the same way. Clients branch on `code` (`validation_error` vs `malformed_request` etc.), never on `message`. `RequestIdMiddleware` is outermost, so every response carries `x-request-id`, and the body echoes it.
- **`Idempotency-Key`** (ADR 0032) is shared middleware (`app_web::Idempotency`, built by `Context::idempotency()`): any POST, PUT, PATCH or DELETE gets it with no code. The first request with a key runs; its 2xx answer is replayed for 24 hours to a retry with the same key and request (method, target, `If-Match`, body); the same key with another request is `idempotency_key_reused` (422), one still running `idempotency_key_in_flight` (409); a failure keeps nothing. Keys are the caller's (the bearer token's subject, else one anonymous scope). `server::build_service` wraps the `Endpoints` in `app_web::Idempotent`, which documents the header and refusals on every unsafe operation.
- Request/response types expose ids, timestamps and versions as `string`. Past 12 modules, nest sub-tuples in the `Endpoints` tuple (std's `Default` cap; poem-openapi's is 16).
- **Every operation is an MCP tool** (ADR 0034), served at `/mcp` by `app_web::mcp` with no code per operation: listed from the spec, each call sent in-process through the same endpoint `/api` is served by, so auth, `If-Match` (the tool's `expected_version`), `Idempotency-Key` (its `idempotency_key`), validation and the `ErrorBody` behave as over REST. So every operation declares `operation_id` (snake_case, verb first, unique: `edit_note`), the tool's name and a public contract, and a summary written for an agent as much as for a person; `composed_app.rs` fails on one missing either and lists every tool, so the surface shows in a diff. Keep an operation off MCP only through `REST_ONLY` in `crates/server/src/tools.rs`, with its reason; one whose body isn't JSON must be listed there. Every `/mcp` request needs a valid bearer token of the subject who opened its session. A new refusal status needs its line in the instructions there (a composed test fails otherwise).
- **Auth** (ADR 0025, 0041): one JWT Bearer scheme (`app_web::JwtAuth`), whose checker resolves the token's claims to a `Principal` through an `Arc<dyn PrincipalResolver>` in request data, or by default the `Authorizer` there: `sub` is the id, the roles are `user` plus those `access` assigns the subject, read from the rule set in force, so no request reads the database for them. The server's resolver is `access::sign_ins` (put in request data by `access::module` through `Module::providing`), which also records the subject as seen (with the token's `name` and `email` claims), writing nothing for a subject recorded within the hour. A token's `roles` claim is ignored (`Claims` has none). `APP_BOOTSTRAP_ADMINS` (comma-separated subjects, `Authorizer::with_bootstrap_admins`) always hold `admin`. Don't build a user store or token issuance unless asked; in dev the Vite proxy signs every `/api` request as the seeded Alice (`frontend/vite.config.ts`), whom `crates/reference/users`' seed assigns `admin`, and tests issue tokens with `JwtVerifier::issue(subject, ttl)`, or, carrying a profile, `JwtVerifier::sign(&Claims::lasting(subject, ttl)?.named(..).with_email(..))`.
- **Authorization** (ADR 0040; engine `app-authz`), at the module and action levels. Every operation has a security requirement unless it is in `PUBLIC` (`crates/server/src/public.rs`) with its reason; `composed_app.rs` fails on one with none that isn't listed, and on a listed one that has one. So for every operation:
  - **Its handler takes the module's `Caller`** (`web/access.rs`: `pub struct Widgets; impl Gate for Widgets { const MODULE: &str = "widgets"; }`, `pub type Caller = app_web::Caller<Widgets>;`), never `JwtAuth`. It yields the `Principal` only once the gate (`module:<name>` / `use`) allows its roles: no token is `401`, a refused gate `403`.
  - **Its use case takes `&Principal`** first and plans its action before it loads or begins anything (`self.authorizer.authorize::<Note>(principal, NoteAction::Edit)?`: `Denied` is `403`). The service holds `ctx.authorizer()`. Reactions pass `Principal::System`, which policies don't apply to.
  - **A row is checked once loaded, before any domain action** (`self.authorizer.check(principal, &plan, &note)?`, in `crates/reference/notes`' `load_for`): refused, it is `404` when the principal may not `view` that row either (the resource's `Resource::VIEW`), so its existence isn't revealed, and `403` when they may. So an author's archived note is `403` to edit (the policy's deny rule answers before the domain's `409`, which stays for `Principal::System`), another user's `404`. Say both in the operation's summary.
  - **A list asks for its rows** (`self.authorizer.rows::<Note>(principal, NoteAction::List)?`, `Denied` is `403`) and hands them to its repository, which pushes them into its SQL with `app_db::push_scope::<XColumns>` (see "Lists"). `XColumns` (`impl app_db::Columns` in `db/`) maps each of the resource's `ATTRS` to a column or a module-authored expression, with its kind, so a policy's value is bound as the column's type and never written into the SQL. Its DB tests check it with `XColumns::assert_every_attribute_is_mapped()` and `app_authz::testing::assert_lists_agree` (the `testing` feature): for several principals and every action, the scoped query holds exactly the rows `Filter::matches` does in memory, so the SQL and the row check can't drift. Rerun it after adding an attribute, scope or rule.
  - A read module's or a projection's search has no `Columns` yet: it refuses any plan but `Allowed` (`crates/reference/note-search`, the template's `search`) rather than show rows the caller may not see.
  - **Its action exists and is granted by default**: the resource's closed `Action` enum (`impl app_authz::Resource` in `domain/access.rs`, beside the aggregate; a read module's on its read model) has it, and the module's default grants, its `policies/default_grants.yaml`, grant it, usually to `user` and `admin`. `migrate` applies each default once (Default Grant): editing a default already applied changes nothing deployed, a new one is granted by the next `migrate`, and one an admin revoked stays revoked. Removing an action leaves its stored grants stale (listed, skipped) until an admin revokes them. A module's `policies()` in `di.rs` builds its `Policies` from `policies/` with `app_authz::policy_file!`, registered with `Module::with_policies(policies)`; `make check-modules` fails on a module with operations and none. The server, worker and `migrate` refuse to start on policies that don't load, naming the module, file and line.
  - **Its row in `OPERATIONS`** (`web/access.rs`, registered with `.performing(OPERATIONS)`): the operation id, resource and action, what ticket 0029's catalog will show an admin. `composed_app.rs` fails on a guarded operation missing from it, or naming an action no policy has.
  - **Grants, roles and assignments are data** (the platform's `access` module, `crates/platform/access`): admins grant and revoke over `list_grants`, `grant_access`, `revoke_grant` and `get_access_catalog` (and the SPA's `/access`), refused `400` naming the field when the role doesn't exist or the catalog lacks the rest, and `409` when equal to a grant made. Roles are records there too (`list_roles`, `create_role`, `delete_role`): a grant's role must name one (a foreign key in `access`' own schema), `admin` and `user` are built in, a role a grant names can't be deleted, and `migrate` creates a role a default grant names when it first applies that grant. A test granting a role of its own creates it first (`create_role`). Who holds a role beyond `user` is an assignment there (`assign_role`, `unassign_role` with `If-Match`; `list_subjects` lists everyone signed in, assigned a role or a bootstrap admin, with their roles): `user` is refused `400`, a role that doesn't exist `400` naming `role`, deleting a role an assignment names `409`, and unassigning a bootstrap admin's `admin`, or the last stored `admin` while `APP_BOOTSTRAP_ADMINS` is empty, `409`. A seed assigns its users' roles through `access_api::RoleAssignments` as `System` (`crates/reference/users`' `module(access::assignments)`; `Module::with_seed` is given the `Context`), a journey through the admin's API or that Module API, never in a token. Each process starts from every module's baseline rules (`server::authorizer`); a server instance then reads the stored grants and assignments before it serves (`server::rules`, `Rules::refresh`) and every `access::POLL_EVERY` (5 s) after, rebuilding its rule set, assignments included, when `access.revision` has moved, keeping the old one on a failed read. The worker doesn't poll: it acts as `System`. `access`' own gate and actions are `admin`'s by baseline rules, so no revocation locks admins out. A module's own tests have no `access`: their driver compiles its defaults in memory (`Authorizer::from_policies`) and gives a signed-in user roles with `Authorizer::assign_in_memory`. Never hand-roll a role check in a module.
- **Pinned** (ADR 0026): `poem` `3.1.x` ↔ `poem-openapi` `5.1.x` (released in lockstep); the `opentelemetry` crates `0.33.x` ↔ `tracing-opentelemetry` `0.34.x`; MSRV 1.94, set by `sqlx` 0.9.

### Running and deploying

- **Migrations run explicitly** (`make migrate`, a pre-start task in a deployment), never on server startup (ADR 0021). Each module migrates its own schema; then `migrate` registers topics and subscriptions and applies the default grants this build adds (`server::apply_default_grants`). A migration file applied anywhere is immutable, its comments included (sqlx checksums it). `SQLX_OFFLINE=true` is the default; regenerate `.sqlx` with `make prepare`.
- **MCP sessions live in the process that opened them** (ADR 0034): behind several server instances, the load balancer routes by the `Mcp-Session-Id` header. `APP_PUBLIC_URL` sets the URL MCP clients are told to sign in for; unset, each request's `Host` and `X-Forwarded-*` say.
- **A worker refuses to start when its clock is more than a minute from the database's** (`Worker::check_clock`), and skips compaction while it is: workers judge leases, due times and retention by their own clocks (ADR 0020), so they must agree to well within the 5-minute lease. The database is only the reference; a wrong database clock stops every worker, which is accepted.
- **One image, three processes**: `server`, `worker` (its own deployment, scaled by replicas sharing the queue, or run by an external timer with `--drain`) and the one-off `migrate` (and `seed`, built with `SEED=true`, which refuses `APP_ENV=prod`). A server built without `embed-frontend` answers `/` with a page pointing at Vite.
  - `worker --drain [--max-seconds N]` (`Worker::drain`) runs the poll loop's pass (`run_until_idle`, then compaction if due) until nothing is due by its clock, then exits `0`, so cron or a container scheduler can drive it with no state outside Postgres. `--max-seconds` caps it: once spent it exits `0`, dropping what is in flight as a stopped worker would (the handler's writes roll back; its job runs again after the 5-minute lease, the attempt counted). Failed jobs are retried and dead-lettered as usual and never change the exit code; it exits non-zero only when it can't work at all: the database unreachable, a subscription unregistered, or its clock refused, each logged with its cause. `--max-seconds` without `--drain` is a usage error (exit `2`). Without flags, `worker` polls as before.

### Traces and metrics (Spec 0003)

Each binary holds `server::telemetry::init(env, "<binary>")` until it exits, called before it connects the pool or builds the app: dropping it flushes and stops the trace and metric pipelines, and `Telemetry::flush()` flushes without stopping. It is configured only by the standard `OTEL_*` variables (`.env.example`); with no `OTEL_EXPORTER_OTLP_ENDPOINT` nothing is exported and log lines carry no `trace_id`. Every HTTP request is already one span (`app_web::TraceRequests`), named by its route template (`DELETE /api/access/roles/{name}`), continuing a caller's `traceparent`. A trace crosses the outbox: `PgEventPublisher` records the current span's W3C context in the envelope (`traceparent`/`tracestate`, CloudEvents' distributed-tracing extension; none outside a trace, as in seeds), and the worker's span for each run of a job (`job`: queue, event type, key, version, attempt) is its child, each retry a sibling, or a new trace's root when the envelope has none (`crates/common/db/src/trace.rs`). The worker also spans each `relay_batch` (only when there is one), `backfill_chunk` and `compaction`. Each SQL query made inside a span, on the pool, a connection or a `Tx`, is a client span under it, named by the statement's first keyword (`SELECT`), with `db.system.name` and `db.query.text`, the statement with its `$1` placeholders and never their values: `app_web::QuerySpans` builds it from the `sqlx::query` event sqlx emits as a query finishes, so a query outside any span (an idle worker's poll) records none. So `RUST_LOG` filters each layer, not the registry, and never hides those events from it; and a value written into SQL text rather than bound (`QueryBuilder::push`, `format!`) would be exported: always bind. To add a span to backend code:

- Use `tracing`, never the `opentelemetry` API: every `tracing` span becomes an OpenTelemetry span, a child of the current one, and its fields its attributes. `#[tracing::instrument(skip_all, fields(note_id = %id))]` on a function, or `let span = tracing::info_span!("relay_batch", queue = %queue);` then `.instrument(span)` on a future (never hold `span.enter()` across an `.await`).
- A value known only later is declared `field::Empty` and recorded with `span.record("rows", n)`; a field not declared up front is dropped. Use OpenTelemetry's semantic-convention name where one exists (`http.route`, `db.query.text`), and `otel.kind` / `otel.status_code = "error"` for the span's kind and status. `otel.name` renames a span only before it starts (first entered); after, `span.context().span().update_name(..)` (`tracing_opentelemetry::OpenTelemetrySpanExt`).
- `skip_all` and name each field: never a token, a secret, a bound SQL value or personal data beyond the principal's subject.
- Test it with `app_web::testing::Traces::install()` (the `test` feature), which captures this thread's spans in memory, then `traces.span(name)` and `Traces::attribute(&span, key)`: copy `a_request_is_one_span_with_its_operation_continuing_the_callers_trace` in `crates/server/tests/composed_app.rs`, or for the worker `crates/common/db/tests/delivery/traces.rs`.

Metrics go to the global meter provider `init` installs (a no-op one when nothing is exported), read by a periodic reader on a thread of its own, so recording one only adds to an aggregate in memory. Measured today: `http.server.request.duration` (`TraceRequests`, by `operation_id`, `http.request.method`, `http.route`, `http.response.status_code`), `mcp.server.tool.calls` (by `gen_ai.tool.name` and `outcome`), `db.client.connection.count` / `.max` (`app_db::observe_pool`, which `app_db::connect` calls) and `db.client.connection.wait_time` (`app_web::PoolWaits`, from the `sqlx::pool::acquire` event a pool built with an `acquire_time_level` emits), `idempotency.replays` and `idempotency.reuse_refusals`. To add a metric (copy `crates/common/web/src/metrics.rs`):

- Build the instrument from `opentelemetry::global::meter("<crate>")` in the constructor of what records into it (a middleware, a service), never in a `static` or `LazyLock`: an instrument records into the provider that was global when it was built, so one built before `init` records nothing, ever. A gauge of state (a pool, a queue) is an observable instrument whose callback reads it at each collection.
- Use OpenTelemetry's semantic-convention name, unit (`s` for durations, as an `f64` histogram; `{request}` for a count) and attribute names where one exists; otherwise a dotted name of the area (`idempotency.replays`). Keep attributes to small closed sets (an operation id, a status, a tool name), never an id, a path, a subject or anything a client chooses: each distinct set is a series kept for the life of the process.
- Test it with `app_web::testing::Metrics::install()` before building the app, then `metrics.names()` after exercising it: copy `every_request_side_metric_is_recorded` in `crates/server/tests/composed_app.rs`. The provider is global, shared by every test of the binary, so check a metric is there, not its value.

## Tests (ADR 0004, 0029, 0031)

Tests are **outside-in**: a module is tested only through its `Endpoints`, through every real layer, against real Postgres. One target per module, named after it: `tests/<module>/` with `main.rs`, `driver.rs`, and `behaviours/` holding one file per behaviour area. Copy `crates/reference/notes/core/tests/notes/`.

- **Each DB test is `#[app_test_db::test(crate::driver::TEMPLATE)] async fn name(pool: PgPool)`**, never `#[sqlx::test]`. The driver's `TEMPLATE` (`Template::new("<module>", |pool| ..)`, its name unique across test binaries) migrates and seeds once per test binary, and each test gets a copy of it with a pool of its own. `sqlx::test` migrated and seeded every test from empty and shared one 20-connection pool among a binary's tests, so tests holding several connections timed out. Anything a test changes per run (clock, subscriptions) stays in the driver's boot, not the template.
- **The driver alone knows HTTP.** It boots via `X::seeded(pool)` (a `Context` with a `FixedClock` after the seeds and `with_authorizer(..)` from the module's own `policies()`, its worker from `handlers(&ctx, ..)` registered with `app_db::register_subscriptions`), exposes domain verbs, and returns `Result<XJson, Refusal>` with only the variants the module produces, mapped in `From<Refused>` from the error `code`, not the status. The transport is `app_web::testing` (the `test` feature, dev-dependencies only): `TestApi::new(XEndpoints, ctx.idempotency(), wire)` mounts them as the server does (`wire` adds the provider, a `JwtVerifier` and `ctx.authorizer()`; requests carry real tokens, as a `user` unless a test signs in with roles, which the driver assigns in memory), and `send()` checks every refusal has the error shape and echoes the request id; `answered()` returns the whole answer, for comparing a retry with the original. Response bodies are `json_newtype!(pub XJson)` with `From<Aggregate>`, lists `Page<XJson>`.
- **Tests speak the domain**: a name states one behaviour (`an_edit_without_a_title_is_rejected_and_changes_nothing`); bodies never mention routes, methods or status codes. Compare whole against seeds (`Ok(seed::alices_note().into())`), or use `assert_json_matches!` / `assert_json_exists!` / `assert_json_not_exists!` for unpredictable or must-not-leak fields. A refused action is checked to have changed nothing and announced nothing; a state change, to have announced its event at its version (`announced::<E>()`).
- Background work runs only when a verb runs it (`run_pending_events()`); time moves only via `later(by)`. A subscriber's driver publishes the provider's event itself (`notes.user_deleted(USER_ID_ALICE)` in `crates/reference/notes`), as it stubs an `-api` trait.
- **No stand-ins for Postgres.** The only stand-ins are a consumer's driver stubbing an `-api` trait, and a hand-written Fake for an external dependency that can't run locally (`crates/reference/users`' `FakeMailer`). No service tests unless a use case has neither an HTTP entry point nor a worker verb. Inline tests only for pure domain logic (`proptest` when the state space is combinatorial), and for shared plumbing a driver can't provoke (`Handlers`).
- **Journeys** exist because each module's tests stub what's across their boundaries, so none notices a payload drifting from what its subscriber expects or the server's wiring breaking. A journey walks one path across modules on the composed app (its modules, the real worker, real JWT, nothing stubbed), asserting every step and re-testing no rules. The app's go in `crates/server/tests/journeys/`, over the registered modules (`server::Registered`; `server` sets `autotests = false`, so the target goes in its `Cargo.toml`), one file per journey area with a driver beside them, `App::seeded(pool)`. Copy `crates/reference/journeys/tests/journeys/`, which composes the reference modules (`reference_journeys::Reference`, a `server::Composition` of its own) so they keep running however the server's change; run them with `cargo test -p reference-journeys`. The composed-app test (`crates/server/tests/composed_app.rs`) fails when a registered module's provider or migrations don't reach the server.

**Seeds** (ADR 0028). Every module that owns data has `src/seed.rs` behind its `seed` feature (enabled for its own tests by a self dev-dependency): `const` ids, one `fn` per aggregate, and `seed::standard(&pool)`, which saves what's missing. Build seeds with the real constructors at fixed `app_domain::seed_time(minutes)`, with ids from `app_domain::well_known_id(MODULE, kind, sequence)`, where `pub const MODULE: u32` is unique across modules. Name each id constant `<OWNER>_<CLASS>_<IDENTIFIER>` (`USER_ID_ALICE`, `ALICE_NOTE_ID_SHOPPING_LIST`, `SHOPPING_LIST_ITEM_ID_MILK`), so the class never reads as part of the identifier. Refer to seeded data by constant, never captured ids. `seed::standard` publishes each aggregate's creation event as of its creation time, so a projection holds seeded data too; a test `TEMPLATE` relays them before the driver registers its subscriptions (an environment seeded before this build), and `announced` leaves them out (`Worker::outbox_end`, `published_after`). A module with an `-api` publishes its seed there under the `-api`'s `seed` feature (`MODULE`, the ids as `Uuid` consts, one `fn` per entity returning its published record); a seed or test names another module's seed data only through its `-api`. A module seeds only its own data; the roles of the accounts it seeds are `access`' data, so its module seed assigns them through `access_api::RoleAssignments` (`crates/reference/users`' `seed::assign_roles`), apart from `seed::standard`, which its own tests' `TEMPLATE` runs without `access`.

## Adding a module

`make new-module NAME=widgets` (Postgres up) copies `crates/module-template/{core,api}` (workspace crates, packages `widgets` and `widgets-api`, compiled and tested but registered with no server) into a module that compiles, passes its tests and is registered everywhere: every layer, a gate, a resource policy with no rules, default grants for `user` and `admin` and an `OPERATIONS` table, a versioned aggregate with create/read/rename/list publishing its events, a projection of its own topic behind a search operation, migrations, seed and tests. It allocates the next module number, applies the migrations to the dev DB and refreshes `.sqlx`. Then:

1. Reshape the aggregate, keeping its migration, seed and tests in step; `make prepare` after changing a `query!`. Keep the search projection only if the module needs a read shape its tables can't serve, point it at another module's topic to search by that module's columns, or delete it (its migration, `db/search.rs`, `handlers(..)`, the operation and its tests).
2. If it uses another module, depend on that module's `-api` and pass the provider's constructor to its `module(..)` in `crates/server/src/modules.rs`, after the module it uses.
3. `make generate`; for a UI, follow `frontend/AGENTS.md`.
4. If it reacts to, provides for, or is read by another module, add or extend a journey.
5. Done when `make check` passes.

`make new-module` refuses a name a platform module has (`access`). A read module isn't scaffolded: copy `crates/reference/note-search`. Registered by hand or not, a module is listed in `crates/server/src/modules.rs` (`Endpoints` tuple and `modules()`), in `crates/server/Cargo.toml` (dependency, and `seed` feature if it has a seed), in the root `Cargo.toml` workspace dependencies (core and `-api`) and in both `deny.toml` lists; `make check-modules` fails on any missing entry.
