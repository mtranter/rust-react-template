# CLAUDE.md

A clone-and-go **template**: a Rust modular-monolith backend (Poem + poem-openapi) whose OpenAPI spec drives a type-safe Vite + React + TypeScript frontend. Keep design decisions minimal; this is a template, not a product.

This file holds the rules. `spec.md` holds the detail and the rationale (cited as §n / Dn below); `CONTEXT.md` is the glossary. **Copy the reference code** rather than working from prose: `notes` is the reference write module (layers, optimistic concurrency, lists, using `users-api`, tests), `users` the provider of a `<module>-api` crate and the auth-guarded route, `note-search` the read module, `frontend/src/features/notes` the reference feature. If the docs and the code disagree, the code wins: fix the doc in the same change.

## Commands

- `make setup` — once after cloning; installs the repo-local Rust tools (§10). `lefthook` is installed separately (`brew install lefthook && lefthook install`).
- `make dev` — migrate, seed, generate the client, then backend `:8080`, the `worker` and Vite `:5173`.
- `make check` — every step CI runs, backend and frontend. **Run it before calling work done.**
- `make generate` — after any backend API change (dump spec → `frontend/openapi.json` → `frontend/src/api/`).
- `make prepare` — after changing any `query!` (refreshes the checked-in `.sqlx` cache; needs a migrated DB).
- `make new-module NAME=<module> [ENTITY=<aggregate>]` — scaffold and register a write module (see "Adding a module").
- `make migrate` / `make seed` / `make build` / `make check-sql` / `make check-deps` / `make check-modules` / `make db-up|db-wait|db-down`.
- Tests: `make test` (both), `make test-backend`, `make test-frontend`.
  - One backend crate/test: `make db-wait`, then `SQLX_OFFLINE=true DATABASE_URL=postgres://app:app@localhost:5432/postgres cargo test -p users registering::` (any substring of the test path). Always point at the `postgres` database, never `app`; without `SQLX_OFFLINE=true`, `query!` fails with `relation "users.account" does not exist`.
  - One FE test (from `frontend/`): `pnpm vitest run src/features/notes -t "lists notes"`. Also `pnpm run typecheck`, `pnpm biome ci .`.
- Run Rust CLI tools as `cargo bin <tool>` (e.g. `cargo bin cargo-deny check`), never a global `cargo deny`/`sqlx`. To bump one, edit `[workspace.metadata.bin]` in the root `Cargo.toml` with a range qualifier (`^0.20`) and re-run `make setup`.

Gotchas:
- A test hanging ~30s then panicking `PoolTimedOut`: Postgres isn't up (`make db-up`).
- Two test runs against one server at once (two worktrees, cargo-watch beside `make test`) collide: per-test database names derive from the test path.
- Failed or renamed tests leave `_sqlx_test_*` databases behind: `make test-db-clean`.

## Architecture rules

Breaking these defeats the template's purpose.

**Layers (§4, D6).** Each module is a crate (`crates/modules/<module>/core`, package `<module>`) with layer folders `web/`, `application/`, `domain/`, `db/`, each re-exported from its `mod.rs` (`crate::domain::User`, never `crate::domain::user::User`). Dependencies point inward: `web → application → domain`, `db → application`. A use case flows handler → service → repository. Grow a layer by adding files by concern, not by growing one file.
- `web/` — `#[OpenApi]` on a **unit struct** `XEndpoints`; the service comes from `Data<&XService>`, never struct state. Request → command → service → HTTP. No business logic. Every operation returns `app_web::ApiResult<T>`, so every one declares the shared `ErrorBody` error responses; `?` converts an `AppError`.
- `application/` — `XService` holds `Arc<dyn XRepository>` (a trait object, not a generic), `Arc<dyn EventPublisher>`, `Arc<dyn Transactions>` and `Arc<dyn Clock>`. One method per use case: load → domain action → save and publish in a unit of work (`begin` … `commit`). It mints ids, reads `self.clock.now()`, and owns cross-aggregate rules. The `Repository` trait lives here: `get → Option<Versioned<X>>`, `save(&mut Tx, &X, Expected) → Version`, `list(&ListQuery<XSortKey>) → Listed<Versioned<X>>`; reads run on the pool, writes take the `Tx`. `error.rs` maps the domain error onto `AppError` exhaustively, pinning it to the input at fault with `AppError::invalid_field(path, msg)` where it can (`path` as the client names it, e.g. `authorId`).
- `domain/` — pure and synchronous: no repositories, no async, no `Utc::now()`, no `XId::new()`, never `poem`/`sqlx`. Constructors take the id and `now`; `restore(..)` rebuilds persisted state.
- `db/` — the only raw SQL; a write runs on `app_db::conn(tx)`. `save` is an INSERT (`Expected::New`) or a version-guarded UPDATE (`Expected::Version`), never an upsert. Map a constraint violation by its name with `app_db::map_db_error` (copy `users`); anything else is `AppError::internal`. A crate with `migrations/` needs `build.rs` (`cargo:rerun-if-changed=migrations`).
- `di.rs` builds the service in a `provider(ctx, ..)` from the shared `app_module::Context` (pool + clock), its worker handlers in a `handlers(ctx, ..)`, and bundles them with the migrations and seed in `module(..) -> app_module::Module`; `lib.rs` exports only the `Endpoints`, public domain types, migrations, `di.rs` constructors, the ports a driver fakes, and `pub mod seed` under the `seed` feature (none of the last three for a module that owns no data). An external system other than the database is a port in `application/` with its adapter in a folder named for it (`users`' `mail/`).
- `#![allow(clippy::disallowed_types)]` only in `db/mod.rs`, `di.rs`, `seed.rs` and test `main.rs` — never under `application/` or `domain/`.

**Optimistic concurrency (§4).** Every write module versions its aggregates; there are no blind overwrites. The version lives in `app_persistence::Versioned`, never in the aggregate. Single-resource responses are `app_web::WithETag<XResponse>`, with `version: string` mirrored in the body. Edits read the expected version only from `If-Match` via `app_web::if_match_version` (absent → 428, stale → 412), never from the body. Copy `notes`.

**Side effects and reactions (§4, D9).** Anything that must follow a write goes in the same unit of work, so it happens if and only if the write commits: never call an external system or another module after `commit`.
- **Every state change publishes an event**, in the unit of work that saves it: each use case that saves an aggregate root calls `self.publisher.publish(&mut tx, events::pending(&x, event))` with the `Tx` it saved in, one event per root changed. The domain decides the event: each transition returns a variant of the aggregate's plain `#[must_use]` `XEvent` enum in `domain/` (constructors `(Self, XEvent)`, mutations `XEvent`, or `Option<XEvent>` where they may change nothing (`notes`' `archive`), deletion `x.delete() -> XEvent`), carrying only what the state can't say; `application/events.rs` maps it exhaustively to the topic's enum and publishes `PendingEvent::on::<XTopic>(&state, event)`. The event is a past-tense fact, never a command in disguise (`UserRegistered`, not `SendWelcomeEmail`).
- **Each aggregate root has a topic**, declared with `app_events::topic!` in your `-api`'s `events::v1` (copy `users_api::events::v1`): its name (`users.user.v1`), `source` (`/users`), entity, key (the root's id) and one line per event (`UserDeleted => Deleted: "users.user_deleted"`, `ItemRemovedFromList => ItemRemoved(ItemRemoved): ".."` for one with a context). It generates `UserTopic`, the exhaustive, deliberately not `#[non_exhaustive]` `UserEvent` enum (a new variant breaks every whole-topic consumer, in the same change), `UserEventKind`, and a marker per event (`UserDeleted`) implementing `app_events::Event`. Versioning is the topic's: events and the entity only gain fields, each `#[serde(default)]`, and a new event is additive; removing one or changing the entity incompatibly is a new topic (`users.user.v2`) published beside the old.
- What an event carries is an `app_events::EventPayload { entity, context }` (event-carried state transfer). `entity` is the root's whole state as it now is, every property but the audit ones (created/updated at/by): the topic's state type (`users_api::events::v1::User`), separate from the published view record, plain `pub` fields; build it from the aggregate in `application/events.rs`. A deletion carries the state as it was last. `context` says what happened where the state can't (`ToDoItemRemoved` carries the list, and `ItemRemoved { item_id }`), held by the variant; none where the entity says it all. The publisher wraps each in a CloudEvents 1.0 `app_events::EventEnvelope` (id, source, type, subject, time, `topic`, `partitionkey`, data).
- Anything else that must follow a write (mail, another module's reaction) is a subscriber, in another module or your own: it implements `app_persistence::Handle<E>` for one event (receiving an `app_events::EnvelopeOf<E>`; the state is `event.data.entity`) or `Handle<XTopic>` for a whole topic (receiving a `TopicEnvelope<XTopic>`, whose `event` it matches with no wildcard arm) in its `application/`, and registers it in its `handlers(..)` under a stable queue name (`Handlers::new().on::<UserDeleted>("notes.archive_deleted_authors_notes", service)`). `migrate` registers subscriptions in `messaging.subscription`; a queue is bound to one topic forever, a retired queue's name is never reused, and a new one gets only events relayed after it. Retire one with the migration in spec §4, never by just deleting the handler. There are no jobs or scheduled work; don't add them until a module needs "do X at time T".
- **Every event carries its root's version**: `PendingEvent::on::<XTopic>(version, &state, event)` takes the `Version` `save` returned, or for a deletion the one removed `.next()`, so it's the newest of its key. Every write to an aggregate, a child's included, saves the root with its version guard: that's what orders its events.
- Handlers run in the worker (`make dev` runs it; `server`'s `worker` bin in prod) inside their own `Tx`, at least once, **in order per key within each queue**, with no order across keys, topics or queues, and gaps where a subscription is filtered or newer than the key: make them idempotent. They're retried with backoff (a failing one holds up only its key), then dead-lettered in `messaging.job` (the delivery queue). A subscriber keeping a copy of another module's state stores the version and applies each event in one `INSERT … ON CONFLICT (id) DO UPDATE … WHERE copy.version < EXCLUDED.version`, with a tombstone for a deletion, since a rerun dead letter arrives out of order; reactions to facts (mail, archiving) don't compare versions.
- Never write another module's data, through its `-api` or otherwise: publish, and let the owner react. Copy `users` (register → `UserRegistered`, which `users` itself handles by mailing a welcome behind the `Mailer` port; delete → `UserDeleted`) and `notes` (`application/reactions.rs`).

**Lists (§4).** Take `ListQuery<XSortKey>` and return `Listed<T>`; build the SQL with `QueryBuilder` + `app_db::push_list_clauses` (the one sanctioned runtime SQL) ending in a unique tiebreak; the handler takes separate `limit`/`offset`/`sort` params and returns `ListResult<XResponse>`. Copy `notes`.

**Isolation (§4).** Keep all three mechanisms passing: the Cargo graph (`make check-deps` fails a module core depending on another core, an `-api` crate depending on anything but pure crates, and a write module declaring `reads`); `deny.toml` (every module core crate, read modules included, in both the `sqlx` and `poem` `wrappers` lists, never an `-api` crate); a per-crate `clippy.toml` (copy a sibling's) under `-D warnings`.

**Cross-module (D1, D7, D8).**
- **Which mechanism?** Choose by why the data is needed, not how much. If a module's business logic needs to know something about another module's data, to decide or validate, call the provider's `<module>-api` trait, at any size (a bulk need gets a batch method like `users_exist(ids)`, not a view). If an endpoint lists, searches, filters, sorts or pages by another module's columns, it belongs in a read module joining the providers' published views (data products). A read module reads others' data only through views, even for one row, never calls `-api` traits and never writes another module's data; a write module never reads views.
- No foreign keys between modules: a cross-module id is a plain `uuid` column, validated on write through the provider's trait where the rules need it, and consumers tolerate it dangling.
- Use another module only through its pure `<module>-api` crate (no poem/sqlx), never its core crate. Ids cross as plain `Uuid`; each side keeps its own typed ids and converts in `application/`. The provider implements the trait in `application/` and exposes a constructor from `di.rs`; `server` passes it to the consumer's `module(..)` (`notes::module(users::directory)`). The consumer's driver stubs the trait; the provider tests its implementation against Postgres.
- A write module never joins across schemas. A **read module** owns no source data and has no domain (a `XFinder` trait returning read models); it joins the provider's versioned published views (`<schema>_api.<name>_v1`, additive changes only, breaking ones as `_v2`). Declare every view read in `[package.metadata.module] reads`; `make check-sql` enforces it. Its only dependency on provider cores is a test-only dev-dependency, for their `migrations()` and `seed::standard`.
- Each published view has a **published record** in the provider's `-api`: `users_api::v1::User` is a row of `users_api.user_v1`. Write it with its version path (`v1::User`), keep it `#[non_exhaustive]`, add a field when the view gains a column, and never return it from a trait (traits have their own types).

**Common crates (§5, D2).** Split pure (`app-domain`, `app-error`, `app-events`, `app-persistence`) from framework-coupled (`app-web` = poem, `app-db` = sqlx, `app-module` = both, for `di.rs` and the server). Never merge them, and never add poem/sqlx to a pure crate (`app-test-support` included). Declare ids with `app_domain::uuid_newtype!`. Config and tracing live in `crates/server`, not `common`.

**Spec → client (§7, §8).** `frontend/src/api/` is generated: never hand-edit it. `build_service()` in `crates/server/src/lib.rs` is shared by the server and `dump-spec`; keep `dump-spec` DB-free (unit-struct `Endpoints`, injected services). Past 12 modules, nest sub-tuples in the `Endpoints` tuple (std's `Default` cap; poem-openapi's is 16). Request/response types expose ids, timestamps and versions as `string`.

**Migrations (§6).** Run explicitly (`make migrate`), never on startup. `SQLX_OFFLINE=true` is the default; regenerate `.sqlx` with `make prepare`.

**Errors (§8).** One `ErrorBody` shape (`code`, `message`, optional `fields: [{path, message}]`, `requestId`) for every failure: handlers return `ApiError`, and `render_error` (applied with `catch_all_error`) renders framework failures — bad JSON, unknown enum values, failed auth, unknown routes — the same way. Clients branch on `code` (`validation_error` vs `malformed_request` etc.), never on `message`. `RequestIdMiddleware` is outermost, so every response, errors included, carries `x-request-id`, and the body echoes it.

**Pinned stack (§2). Keep `poem` `3.1.x` ↔ `poem-openapi` `5.1.x` paired. MSRV is 1.94. hey-api packages are pinned exact.

**Auth (§11).** One JWT Bearer scheme guarding one route. Don't build a user store or token issuance unless asked.

## Adding a module (§4)

`make new-module NAME=widgets` (needs Postgres up) generates `crates/modules/widgets/{core,api}` from `crates/module-template/{core,api}` (themselves workspace crates, packages `widgets` and `widgets-api`, compiled and tested but registered with no server; change them like any module, and `widgets` can't be scaffolded): every layer, a versioned aggregate with create/read/rename/list publishing its events, migration, seed and tests that pass as generated. It also allocates the next module number, applies the migrations to the dev DB, refreshes `.sqlx`, and registers the module in every shared list. Then:
1. Reshape the aggregate, keeping its migration, seed and tests in step; `make prepare` after changing a `query!`.
2. If it uses another module, depend on that module's `-api` crate and pass the provider's constructor to its `module(..)` in `crates/server/src/modules.rs`, after the module it uses.
3. `make generate`, then add `frontend/src/features/<module>/` if it has a UI.
4. If it reacts to, provides for, or is read by another module, add or extend a journey in `crates/server/tests/journeys/`.
5. `make check`.

A read module isn't scaffolded: copy `note-search`. Registered by hand or not, a module is listed in `crates/server/src/modules.rs` (`Endpoints` tuple and `modules()`), in `crates/server/Cargo.toml` (dependency, and `seed` feature if it has a seed), in the root `Cargo.toml` workspace dependencies (core and `-api`) and in both `deny.toml` lists. `make check-modules` fails on any missing entry, and the composed-app test (`crates/server/tests/composed_app.rs`) fails when a registered module's provider or migrations don't reach the server.

## Testing (§13, D3)

- **Outside-in.** Test a module only through its `Endpoints`, through every real layer, against real Postgres. One target per module, named after it (`#[sqlx::test]` names each database from the test path, so a shared name like `tests/behaviours/` would collide across modules): `tests/<module>/` with `main.rs`, `driver.rs`, and `behaviours/` holding one file per behaviour area. Every DB test is `#[sqlx::test(migrations = false)] async fn name(pool: PgPool)`; `migrations = false` is mandatory.
- **The driver alone knows HTTP.** It boots via `X::seeded(pool)` (a `Context` with a `FixedClock` after the seeds, and the module's worker from `handlers(&ctx, ..)`, registered with `app_db::register_subscriptions` as `migrate` does), exposes domain verbs, and returns `Result<XJson, Refusal>` with only the variants the module produces (`Invalid(field paths) | Malformed | NotFound | Conflict | NotSignedIn | PreconditionRequired | Stale`), mapped in `From<Refused>` from the error `code`, not the status. The transport is `app_web::testing` (the `test` feature, dev-dependencies only): `TestApi` mounts the `Endpoints` as the server does, and `send()` checks every refusal has the error shape and echoes the request id. Assert field paths with `Refusal::invalid(["title"])`. Response bodies are `json_newtype!(pub XJson)` with `From<Aggregate>`, lists `Page<XJson>`. Background work runs only when a verb runs it (`run_pending_events()`, i.e. `Worker::run_until_idle`) and time moves only via `later(by)`. A subscriber's driver publishes the provider's `-api` event itself (`notes.user_deleted(ALICE)`) as it stubs a trait; a publisher's exposes `announced::<E>()` (`(Version, payload)` pairs, over `Worker::published::<E>()`) and a free `announced(&aggregate)` building the payload a seed aggregate would carry, and every state-changing behaviour asserts its event and its version, and that a refused one announced nothing. Copy `notes`' driver.
- **Tests speak the domain.** Names state a behaviour (`an_edit_without_a_title_is_rejected_and_changes_nothing`); bodies never mention routes, methods or status codes. Compare whole against seeds (`Ok(seed::alice().into())`), or use `assert_json_matches!` / `assert_json_exists!` / `assert_json_not_exists!` for unpredictable or must-not-leak fields. One behaviour per test, and check that a refused action changed nothing.
- **Journeys** are the one carve-out from "one behaviour per test", and live only in `server`'s `journeys` target: the root `crates/server/tests/journeys.rs` (`mod driver; mod journeys { mod finding_notes; … }`), its driver in `tests/driver.rs`, one file per journey area in `tests/journeys/`. `server` sets `autotests = false`, so a new test target there goes in its `Cargo.toml`. A behaviour test checks one rule within a module; a journey checks that modules compose along a path on the composed app (every registered module, the real worker, real JWT auth, nothing stubbed): each step's result feeds the next, and every step is asserted. Its driver `App::seeded(pool)` migrates, seeds and registers subscriptions for `server::modules()`, builds `server::build_app` and `server::worker` over a `Context` with a `FixedClock`, exposes cross-module verbs (`app.as_user(ALICE).write_note(..)`, `.rename_myself(..)`, `.delete_account()`, `app.search_notes(q)`, `app.run_pending_events()`), carries each version into `If-Match` itself and goes over `app_web::testing` (`TestApi::over`). Journeys are few, only for paths that cross a boundary, don't re-test rules, and are named for the path walked (`a_note_is_found_by_its_authors_current_name`); `cargo test -p server journeys::` runs only them. A path within one module is a behaviour test in that module (`notes`' `behaviours/lifecycle.rs`), and neither a module nor the template has journeys.
- No service tests unless a use case has neither an HTTP entry point nor a worker verb, or two outcomes are indistinguishable over HTTP. No in-memory fakes of Postgres; a hand-written Fake only for an external dependency that can't run locally. Inline unit tests only for pure domain logic (`proptest` when the state space is combinatorial), and for `app-persistence`'s `Handlers`, against a fake `TxBackend`.
- **Seeds.** Every module that owns data has `src/seed.rs` behind its `seed` feature (enabled for its own tests by a self dev-dependency): `const` ids (`users::seed::ALICE`), one `fn` per aggregate, and `seed::standard(&pool)`, which saves what's missing. Build seeds with the real constructors at fixed timestamps (`app_domain::seed_time(minutes)`). Build ids with `app_domain::well_known_id(MODULE, kind, sequence)` (`MMMMMMMM-KKKK-0000-0000-NNNNNNNNNNNN`, §13), where `pub const MODULE: u32` is the module's number, unique across modules. Refer to seeded data by constant, never by captured ids. A module seeds only data it owns (`note-search` has no seed).
- **Seeds across modules.** A module with an `-api` publishes its seed there, under the `-api`'s `seed` feature: `MODULE`, the ids as `Uuid` consts and one `fn` per entity returning its published record (`users_api::seed::alice() -> v1::User`); the core seed builds aggregates from those records, adding unpublished fields. A seed or test names another module's seed data only through its `-api` (`notes`' seed authors notes as `users_api::seed::ALICE`); a read module's tests assert against `-api` seed records, never aggregates.
- **Frontend.** Mock only at the network boundary with MSW, never module or import mocks.

## Frontend (§8)

- Organise by feature: `src/features/<module>/` per backend module, imported via its `index.ts` only. Features never import each other (`pnpm run lint:imports` enforces both); shared code goes in `src/components/`, `src/hooks/`, `src/lib/`. Pages (`src/pages/`) are thin.
- Forms use TanStack Form (copy `src/features/notes/new-note-form.tsx`): save in `validators.onSubmitAsync` and return `submitErrors(error)` from `src/lib/api-errors.ts`, which puts each server field error on the input named by its `path`; pass the form's input names as the mutation's `meta.formFields`. Any other failed mutation is toasted by the `QueryClient` from `src/lib/query-client.ts`.
- Routes are code-based in `src/router.tsx` (TanStack Router); cover each new URL in `router.test.tsx`.
- UI is the vendored shadcn/ui in `src/components/ui/`: use an existing component before writing one, compose rather than restyle, and theme via the CSS variables in `src/index.css`. Server-paged lists use `src/components/data-table/` (copy `notes-table.tsx`).
- Prod embeds the SPA into the binary (`embed-frontend` feature, on in `make build` and the Dockerfile); dev uses the Vite `/api` proxy.

## Comments

Comments are the exception. Write one only when the code can't say it: a surprise (a workaround, a deliberate deviation, a non-obvious constraint), or the source or derivation of a value or algorithm. Don't restate the code, narrate steps or label sections; prefer a better name. Doc comments that only repeat the signature are the same noise.
