# Frontend (`frontend/`)

Rules for the Vite + React + TypeScript SPA; the repo-wide ones are in the root `AGENTS.md`. Paths are from `frontend/`.

**Copy the reference code** rather than working from prose: `src/features/notes` is the reference feature (a server-paged list whose page and sort live in the URL, a create form with server field errors, an edit dialog sending `If-Match` and handling a `412`), with `src/pages/notes-page.tsx`, its route in `src/router.tsx`, its entry in `src/shell/capabilities.ts` and its tests in `src/test/notes-list.test.tsx` and `src/test/note-editing.test.tsx`.

## Commands

Run from `frontend/`, after `pnpm install` once.

- `pnpm run generate` regenerates `src/api/` from the checked-in `openapi.json`, with no backend or database; `make generate` from the root first dumps a fresh spec from the backend.
- `pnpm run test`; one test: `pnpm vitest run src/test/<feature>.test.tsx -t "<part of its name>"`. Also `pnpm run typecheck`, `pnpm biome ci .`, `pnpm run lint:imports`, `pnpm run build`. `make check` from the root runs them all.
- `pnpm run screens` screenshots every scenario in `screens/scenarios.ts` at desktop and phone widths to `screens/out/` (gitignored), for UX review. Needs no backend or database, only Playwright's Chromium: `pnpm exec playwright install chromium` once where it's missing. Not part of `make check` or CI.
- `make e2e` (from the root; part of `make check` and CI) signs in to the real thing: `scripts/e2e.sh` builds the server in debug with `embed-frontend` and `fake-oidc` (`crates/common/fake-oidc`, an OIDC provider that approves at once as one named subject), migrates and seeds a database of its own, and runs `e2e/sign-in.ts`, which starts both, signs in with Playwright's Chromium as that subject (a bootstrap admin), checks `/access/subjects` lists it by the name only its token carried, invites someone from the Invitations area (the server's Cognito adapter pointed at `fake-oidc`'s stand-in) and finds them pending and on the Users page, then signs out from the user menu and checks the signed-out page stays. It needs Postgres (`make db-up`) and Playwright's Chromium. Keep it to the `access` screen, which every app keeps after `make init`.

## Rules

- **Shell** (`src/shell/`, ADR 0046, 0047). The SPA is one suite of apps (CRM, timesheets, billing, rostering), each with a few areas (CRM › Contacts, Deals), and never deeper: a record inside an area is a page of its own under the area's path, not a third level of navigation. An app is a backend Capability's (`crates/capabilities/<capability>/`), and one entry in the registry, `src/shell/capabilities.ts` (`Capability`: its `id`, the Capability's and written as a literal `id: "<id>"`, which `make check-modules` reads to fail on a Capability with no entry or an entry with none; a label, a one-line description, a lucide icon, its `path`, and its `areas` in order, the first where it opens). `make new-module` adds the entry, with the new module's Area, when it makes a Capability; every route of it sits under `/<app>/<area>` (`/crm/contacts`), a record under its area (`/crm/contacts/$contact`, `/access/roles/$role`). Each Area names the one action it needs (`needs: { resource, action }`, as its Module's policies name them, a literal on one line, which `make check-modules` fails on when no registered Module declares it; `make new-module`'s Area needs its entity's `list`). `useCapabilities` asks the server once what the caller may do (`get_my_permissions`, `useMyPermissions` in `src/features/access`, cached a minute), and keeps each Area whose `needs` the answer holds and each app with at least one, opening it at the first; while that is pending it shows nothing rather than everything. The platform's tools (`access`) go in its `platform`, shown apart in the sidebar's footer and on the launcher. Hiding is a convenience, not protection: an Area's URL opened directly still routes, and what its page shows is the server's refusal of its operations. From that list the shell draws everything: the launcher at `/` (`src/pages/home-page.tsx`), the sidebar (`app-sidebar.tsx`: a switcher over the open app's areas, the current one marked; collapsible to icons, ⌘B, and a sheet on a phone), the header's breadcrumb (app › area, the area a link back from a record), and Go to (`go-to.tsx`, ⌘K or Ctrl K, every area of every app). So a new app is its routes in `src/router.tsx` and its entry, and nothing in the shell. An area is a route, never a tab: `Tabs` are only for views of one thing within a page. When a route moves, its old URL redirects, keeping its search (`/home`, `/search`, `/access?tab=`). The header holds Go to, the assistant's toggle, the theme and the user menu, and nothing an app adds.
- **Pages** render inside `Page` (`src/components/page.tsx`): the title, a one-line description of what the screen is for, its primary actions on the right (a create button), then its content; `wide` (the default) for lists and tables, `narrow` for a form or one record. A page never renders `<main>`, the shell's, nor its own header or navigation.
- **Screens.** A change that adds or alters a screen or one of its states adds or updates its scenario in `screens/scenarios.ts` (route, MSW handlers, steps found by role and label, and what the shot `shows`), and runs `pnpm run screens`. The screens entry (`screens/`) renders the real `App` and router over MSW's browser worker; code in `src/` never imports from `screens/`, so none of it reaches the production bundle (`pnpm run lint:imports` enforces it). `scenarios.ts` is also run by Node's type stripping in `shoot.ts`, so it imports only packages, other scenario files (the platform's sign-in screens are in `screens/sign-in-scenarios.ts`, which `make init` keeps), and only types from `@/`. A scenario's `signIn` gives the stand-in identity provider of a signed-in (or signed-out) user; without one the app signs no one in, as in dev.
- **Features.** Organise by feature: `src/features/<module>/` per backend module, imported via its `index.ts` only. Features never import each other (`pnpm run lint:imports` enforces both); shared code goes in `src/components/`, `src/hooks/`, `src/lib/`. A feature needing another module's data calls that module's generated client directly: the API is the contract.
- **URL state.** Pages (`src/pages/`) are thin: they lay out features and own URL concerns, reading route params and search and handing features plain values (`page`, `sort`, a search text) and callbacks. A feature never reads the URL, but may link or navigate to a route with TanStack Router's typed `Link` and `navigate`. UI state a link should reproduce (which page, sort, filter, search) goes in the route's search, validated there: copy `validateListSearch` in `src/components/data-table/list-search.ts`, whose comment says why a dropped value comes back `undefined`, and `listSearch(position)` to write a new position back (as `src/pages/notes-page.tsx` does). A link past the last page says so and offers page 1 (`isPastLastPage`). Open dialogs, unsaved drafts and per-viewer preferences (theme, the sidebar collapsed, the assistant's panel open) don't go in the URL.
- **Forms** use TanStack Form (copy `src/features/notes/new-note-form.tsx`): save in `validators.onSubmitAsync` and return `submitErrors(error)` from `src/lib/api-errors.ts`, which puts each server field error on the input named by its `path`; pass the form's input names as the mutation's `meta.formFields`. Any other failed mutation is toasted by the `QueryClient` from `src/lib/query-client.ts`, except error codes the caller names in `meta.reports` and tells the user about itself.
- **Edits are versioned.** A change to an existing resource sends `ifMatch(version)` (`src/lib/if-match.ts`) with the version last read, never the version in the body. On `412 precondition_failed` (`isPreconditionFailed`) it refetches the resource, says so in `src/components/changed-meanwhile-alert.tsx`, keeps what the user typed, and sends the reloaded version on the next try; it names `"precondition_failed"` in `meta.reports` so it isn't toasted as well (copy `src/features/notes/edit-note-dialog.tsx`).
- **Routes** are code-based in `src/router.tsx` (TanStack Router); cover each new URL, and each new screen's behaviour, in its feature area's `src/test/<feature>.test.tsx` (e.g. `src/test/note-editing.test.tsx`), which renders the real app and router with `renderAt` (`src/test/render-app.tsx`) and the API fixtures in `src/test/fixtures.ts` (`notesApi` answers as the server does, `If-Match` included). `router.test.tsx` keeps its existing tests; new ones don't go there, and the shell's are in `src/test/shell.test.tsx`, over the `access` screens, which survive `make init`. `/home` and `/search` are old aliases of `/notes` and `/notes/search`, keeping their search.
- **UI** is the vendored shadcn/ui in `src/components/ui/`: use an existing component before writing one, and compose rather than restyle. The look is a work tool's: quiet and dense, neutral greys with one accent (indigo) on what acts or is current (`primary`, `ring`, the sidebar's active item), never a colour per app (an app is told apart by its icon); lucide icons, never emoji, and an icon-only button has an `aria-label`; no motion but the components' own. Theme in `src/theme.css` (colours, radius, fonts, shadows, light and `.dark`), never per component; `index.css` maps its variables onto Tailwind's tokens. Refresh the components from upstream with `pnpm dlx shadcn@latest add --all --overwrite`, then `pnpm run format`, and re-check local edits (shadcn may also write its variables back into `index.css`: move them to `theme.css`). The user's light/dark/system choice lives in `src/lib/theme.tsx` (chosen with `src/components/theme-toggle.tsx`, in the root layout), and `index.html` applies it before first paint. Server-paged lists use `src/components/data-table/` (copy `src/features/notes/notes-table.tsx`).
- **Tests.** Mock only at the network boundary with MSW, never module or import mocks (`vitest.setup.ts` stands in for the browser APIs jsdom lacks: `matchMedia`, `ResizeObserver`, `scrollIntoView`, and clears `localStorage` after each test). Feature tests beside a feature (`src/features/notes/notes.test.tsx`) render its components with their position held in state; behaviour that crosses the router lives in `src/test/`. Find elements by role and label, as the user does.
- **Pinned.** hey-api packages are pinned exact, and so is `playwright` (to the version whose Chromium build `pnpm exec playwright install chromium` fetches: 1.64.1, build 1248).
- **Signing in.** Every operation but those in the server's `PUBLIC` needs a bearer token whose subject holds a role granted the operation's action (every signed-in user holds `user`; `access` assigns the rest). At start-up `src/main.tsx` reads `/auth/config` (`fetchSignInConfig` in `src/lib/sign-in/`). With none (a `404`, no client id, or Vite answering with the SPA, as in `make dev`) the app signs no one in and the Vite proxy adds a token to each `/api` request, as the seeded user Alice (`devToken` in `vite.config.ts`). With one, `oidc-client-ts` (pinned exact; the SPA implements no OIDC step itself) signs the user in with the authorization code flow and PKCE as a public client (ADR 0042): `RequireSignIn`, in the root layout, sends a visitor who isn't signed in straight to the provider's hosted page (the app has no sign-in screen of its own), with `state`, a `nonce` and the page they were on; `/auth/callback` (`src/pages/sign-in-callback-page.tsx`) completes it and returns there, or shows the provider's error and a retry button, never redirecting by itself. Tokens live in this tab's `sessionStorage` only. `src/hey-api.ts` adds `Authorization: Bearer <access token>` to every request. The `Session` renews the access token a minute before it expires (`Session.renew`, through `oidc-client-ts`' `signinSilent`): with the refresh token when the provider issued one, otherwise silently in a hidden iframe sent back to `/auth/callback`, where `src/main.tsx` (`isSilentRenewal`) hands the answer to the app in its parent and renders nothing, so the SPA needs no second redirect URI. A request that gets `401` is renewed once and retried once by `src/hey-api.ts` (callers at once share one renewal); if renewal or the retry fails, it sends the user to sign in, back to the same page (the router's path and search), and never loops: `Session.signInAgain` records that sign-in in `sessionStorage` until the API next accepts a token (`Session.accepted`), and if the token the user comes back with is refused too, the `401` reaches the screen rather than sending them round again (a provider whose tokens the API never accepts, such as the wrong audience, would otherwise bounce them for ever). A `403` passes through untouched, and with no `/auth/config` nothing renews and a `401` reaches the screen as it is. The header's user menu (`src/shell/user-menu.tsx`) names the user from the ID token and signs them out: locally, then at the provider when it has an end-session endpoint, ending on `/auth/signed-out`, which never redirects by itself (a live provider session would sign the user straight back in). These routes sit outside the pathless `app` layout route in `src/router.tsx`, so a page's route id is `/app/<path>` (`getRouteApi("/app/access/subjects")`). Tests pass `renderAt(path, { session })` a `Session` over the stub provider in `src/test/sign-in-fixtures.ts` (`src/test/sign-in.test.tsx`); without one, as in every other test, no one is signed in. A create form never sends who is acting: the server takes it from the token (`new-note-form.tsx` sends no author).
- **Access** (`src/features/access`, the shell's platform tool `access`, its areas `src/pages/access-page.tsx`: `/access/subjects`, where `/access` opens, its `search` kept in the URL too; `/access/roles`; `/access/invitations`, people invited by email, with its `status` filter; `/access/permissions`, every grant filtered by role, resource and action; and `/access/roles/$role`, `src/pages/role-page.tsx`, what one role may do, module by module, each action a checkbox, or a select of its scopes, that grants or revokes at once) is the platform's `access` module's screen, not the app's: `make init` keeps it. It names resources, actions and scopes by the catalog's `label`s (`catalog.ts`), never their code names, except a stale grant's, which the catalog no longer has. Its Areas show as the shell shows any (Users needs `subject` / `list`, Roles `role` / `list`, Permissions `grant` / `list`, Invitations `invitation` / `list`), since the SPA reads no roles from its token; each page's list shows the server's `403` as a refusal (`load-failed.tsx`), and its create button shows only to a caller holding that action (`usePermitted`). Tests answer `get_my_permissions` with every Area's `needs` by default (`src/test/may-use-everything.ts`, a setup file beside `vitest.setup.ts`, with `holding(..)` to answer otherwise) and the catalog with a `403`, so a test of an admin uses `accessApi` (`src/test/access-fixtures.ts`, holding `adminPermissions`) and one of a caller who may not `notAnAdmin`; `screens/main.tsx` answers with the apps' Areas' `needs` and not the platform's, so a scenario of an admin answers both itself. In dev the signed-in Alice is an admin: the seeds assign her `admin` through `access` (or `APP_BOOTSTRAP_ADMINS` names her).
- **Assistant** (`src/features/assistant`, route `/assistant`, `src/pages/assistant-page.tsx`) is the platform's `assistant` module's screen, which `make init` keeps (its scenarios in `screens/assistant-scenarios.ts`). The header's toggle opens it as a panel docked beside whatever app is open (`src/shell/assistant-panel.tsx`; a sheet on a phone), so the user can ask about what they see; it stays open, on its conversation, from screen to screen, and whether it is open is remembered per viewer. `/assistant` is its full page, which the panel opens on the same conversation, and where the toggle hides. The toggle, the panel and the page's chat show only while the status operation says it is on (`useAssistantOn`: off, or a `403` for a caller who may not chat, hides them, the page saying it isn't available). `AssistantChat` sizes itself by its container, not the viewport (`@container`), so the narrow panel shows the list or the open conversation, with a way back. `vitest.setup.ts` and `screens/main.tsx` answer that it is off by default, so a test or scenario of it answers `{ on: true }` itself (`src/test/assistant.test.tsx`, with `assistantApi` in `src/test/assistant-fixtures.ts` answering its conversations as the server does). The chat lists the caller's conversations newest first (`conversation-list.tsx`: start, open, delete with `If-Match`) beside the open one's messages and tool calls (`conversation-view.tsx`); which one is open is the route's `?conversation=`. Its chat sends a message at the conversation's version (`If-Match`) and follows the turn's `text/event-stream` (`use-turn.ts`): text as it streams, each tool call a collapsible row (`Running` until its result), errors inline, the input disabled until the turn ends; then it refetches the conversation, whose stored messages replace the streamed ones, and invalidates every query if the turn stored a write that ran (an `approved` call without an error), so other screens show the change. `@hey-api` can't parse an event stream, so `turn-stream.ts` calls the generated `postAssistantConversationsByIdMessages` with `parseAs: "stream"` (keeping its base URL, token and thrown `ErrorBody` for a refusal before the stream) and reads the raw body itself, typing each event's `data` as the generated `TurnEventResponse`. The assistant's words are markdown (`markdown.tsx`, react-markdown with `skipHtml`: never render them as HTML, a tool result may have steered them). A call awaiting approval is a card (`PendingWrite`) describing its `proposal`, which the server builds from the call itself so the user approves exactly what runs (`proposal.tsx`: titled by its action and target, its fields a label/value list with dates in the browser's locale, a changed value struck through before the new one, and never a tool name, JSON, id, version or key; with no proposal it says only that the assistant wants to make a change, and only **Reject** is enabled), with **Approve** and **Reject**, disabled while a turn runs; every other call's row is headed by the same action text (`actionOf`), a read's by its `summary` too, its JSON only inside the opened row; deciding calls `decideToolCall` in `turn-stream.ts` (the generated `postAssistantConversationsByIdToolCallsByToolCallIdDecision`, no `If-Match`: the call's status is its guard, a `409` once decided) and follows the resumed turn through the same `useTurn` (`decide`), the stored call shown as the stream tells it (`decided`, then its `toolResult`) until the refetch; an approved call that ran invalidates every query. A message sent while calls are pending rejects them, server-side. Tests play a turn out with `scriptedTurn()` from `assistant-fixtures.ts`, passed to `assistantApi(conversations, turns)`, whose turns answer messages and decisions in order (`src/test/assistant-turns.test.tsx`, `src/test/assistant-approvals.test.tsx`).
- **Prod** embeds the SPA into the binary (`embed-frontend` feature, on in `make build` and the Dockerfile); dev uses the Vite `/api` proxy.
