# Frontend (`frontend/`)

Rules for the Vite + React + TypeScript SPA; the repo-wide ones are in the root `AGENTS.md`. Paths are from `frontend/`.

**Copy the reference code** rather than working from prose: `src/features/notes` is the reference feature (a server-paged list whose page and sort live in the URL, a create form with server field errors, an edit dialog sending `If-Match` and handling a `412`), with `src/pages/home-page.tsx`, its route in `src/router.tsx` and its tests in `src/test/notes-list.test.tsx` and `src/test/note-editing.test.tsx`.

## Commands

Run from `frontend/`, after `pnpm install` once.

- `pnpm run generate` regenerates `src/api/` from the checked-in `openapi.json`, with no backend or database; `make generate` from the root first dumps a fresh spec from the backend.
- `pnpm run test`; one test: `pnpm vitest run src/test/<feature>.test.tsx -t "<part of its name>"`. Also `pnpm run typecheck`, `pnpm biome ci .`, `pnpm run lint:imports`, `pnpm run build`. `make check` from the root runs them all.
- `pnpm run screens` screenshots every scenario in `screens/scenarios.ts` at desktop and phone widths to `screens/out/` (gitignored), for UX review. Needs no backend or database, only Playwright's Chromium: `pnpm exec playwright install chromium` once where it's missing. Not part of `make check` or CI.

## Rules

- **Screens.** A change that adds or alters a screen or one of its states adds or updates its scenario in `screens/scenarios.ts` (route, MSW handlers, steps found by role and label, and what the shot `shows`), and runs `pnpm run screens`. The screens entry (`screens/`) renders the real `App` and router over MSW's browser worker; code in `src/` never imports from `screens/`, so none of it reaches the production bundle (`pnpm run lint:imports` enforces it). `scenarios.ts` is also run by Node's type stripping in `shoot.ts`, so it imports only packages, and only types from `@/`.
- **Features.** Organise by feature: `src/features/<module>/` per backend module, imported via its `index.ts` only. Features never import each other (`pnpm run lint:imports` enforces both); shared code goes in `src/components/`, `src/hooks/`, `src/lib/`. A feature needing another module's data calls that module's generated client directly: the API is the contract.
- **URL state.** Pages (`src/pages/`) are thin: they lay out features and own URL concerns, reading route params and search and handing features plain values (`page`, `sort`, a search text) and callbacks. A feature never reads the URL, but may link or navigate to a route with TanStack Router's typed `Link` and `navigate`. UI state a link should reproduce (which page, sort, filter, search) goes in the route's search, validated there: copy `validateListSearch` in `src/components/data-table/list-search.ts`, whose comment says why a dropped value comes back `undefined`, and `listSearch(position)` to write a new position back (as `src/pages/home-page.tsx` does). A link past the last page says so and offers page 1 (`isPastLastPage`). Open dialogs, unsaved drafts and per-viewer preferences (theme) don't go in the URL.
- **Forms** use TanStack Form (copy `src/features/notes/new-note-form.tsx`): save in `validators.onSubmitAsync` and return `submitErrors(error)` from `src/lib/api-errors.ts`, which puts each server field error on the input named by its `path`; pass the form's input names as the mutation's `meta.formFields`. Any other failed mutation is toasted by the `QueryClient` from `src/lib/query-client.ts`, except error codes the caller names in `meta.reports` and tells the user about itself.
- **Edits are versioned.** A change to an existing resource sends `ifMatch(version)` (`src/lib/if-match.ts`) with the version last read, never the version in the body. On `412 precondition_failed` (`isPreconditionFailed`) it refetches the resource, says so in `src/components/changed-meanwhile-alert.tsx`, keeps what the user typed, and sends the reloaded version on the next try; it names `"precondition_failed"` in `meta.reports` so it isn't toasted as well (copy `src/features/notes/edit-note-dialog.tsx`).
- **Routes** are code-based in `src/router.tsx` (TanStack Router); cover each new URL, and each new screen's behaviour, in its feature area's `src/test/<feature>.test.tsx` (e.g. `src/test/note-editing.test.tsx`), which renders the real app and router with `renderAt` (`src/test/render-app.tsx`) and the API fixtures in `src/test/fixtures.ts` (`notesApi` answers as the server does, `If-Match` included). `router.test.tsx` keeps its existing tests; new ones don't go there. `/home` is an old alias: it redirects to `/`, keeping its search.
- **UI** is the vendored shadcn/ui in `src/components/ui/`: use an existing component before writing one, and compose rather than restyle. Theme in `src/theme.css` (colours, radius, fonts, shadows, light and `.dark`), never per component; `index.css` maps its variables onto Tailwind's tokens. Refresh the components from upstream with `pnpm dlx shadcn@latest add --all --overwrite`, then `pnpm run format`, and re-check local edits (shadcn may also write its variables back into `index.css`: move them to `theme.css`). The user's light/dark/system choice lives in `src/lib/theme.tsx` (chosen with `src/components/theme-toggle.tsx`, in the root layout), and `index.html` applies it before first paint. Server-paged lists use `src/components/data-table/` (copy `src/features/notes/notes-table.tsx`).
- **Tests.** Mock only at the network boundary with MSW, never module or import mocks. Feature tests beside a feature (`src/features/notes/notes.test.tsx`) render its components with their position held in state; behaviour that crosses the router lives in `src/test/`. Find elements by role and label, as the user does.
- **Pinned.** hey-api packages are pinned exact, and so is `playwright` (to the version whose Chromium build `pnpm exec playwright install chromium` fetches: 1.64.1, build 1248).
- **Signing in.** Every operation but those in the server's `PUBLIC` needs a bearer token with a role granted its module's gate (`user` by default). In dev the Vite proxy adds one to each `/api` request, as the seeded user Alice (`devToken` in `vite.config.ts`); there is no sign-in screen yet. A create form never sends who is acting: the server takes it from the token (`new-note-form.tsx` sends no author).
- **Access** (`src/features/access`, route `/access`) is the platform's `access` module's screen, not the app's: `make init` keeps it. It shows only to a caller who may manage access, which the SPA learns by asking for the catalog (`useManagesAccess`: a `403` hides it), since it holds no token to read roles from; `vitest.setup.ts` and `screens/main.tsx` answer that `403` by default, so a test or scenario of an admin answers the catalog itself (`src/test/access-fixtures.ts`). In dev, `APP_DEV_ROLES=user,admin make dev` signs in as an admin too.
- **Prod** embeds the SPA into the binary (`embed-frontend` feature, on in `make build` and the Dockerfile); dev uses the Vite `/api` proxy.
