# Learnings: 0049 request-side metrics over OTLP

- **OpenTelemetry instruments bind to the provider that was global when they were built.** `opentelemetry::global::meter(..)` before `global::set_meter_provider` gives a no-op instrument forever (no lazy delegation, unlike some SDKs). So instruments are built in the constructors of what records into them (`TraceRequests`, `Idempotency::new`, `OpenApiTools::new`, `app_db::observe_pool`), never in statics, and `server::telemetry::init` must run before the pool and app are built (it does in all three bins).
- **The global meter provider is process-wide**, unlike `Traces::install()`'s per-thread subscriber. `app_web::testing::Metrics::install()` therefore installs one shared in-memory provider for the whole test binary (a `OnceLock`) and tests only check a metric's *name* is present, never its value.
- **An unrecorded instrument isn't exported**: the in-memory exporter only shows metrics with a data point, so the test must exercise each path (replay, reuse refusal, MCP call, a query for the acquire wait).
- **sqlx 0.9 has no acquire hook.** The pool's wait is read from the `sqlx::pool::acquire` tracing event (`acquired_after_secs`), which sqlx emits only when the pool is built with `acquire_time_level(log::LevelFilter::..)` (a `log` level, hence the new `log` workspace dep). `app_db::connect` and `app_test_db`'s per-test pool both set it; `app_web::PoolWaits` is a per-layer-filtered tracing layer, like `QuerySpans`.
- `PoolWaits::layer` takes a `&Meter` explicitly because `telemetry::init` builds the subscriber before it sets the global meter provider (it only sets it once `try_init` succeeds, so a second `init` changes nothing).
- `cargo build` of the whole server from cold takes several minutes; run long builds/tests in the background.
- `make check-changed` runs `make db-up`, which fails when another checkout's Postgres already holds 5432. `COMPOSE_PROJECT_NAME=rust-react-template make check-changed` reuses that running container instead.
