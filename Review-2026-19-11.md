# Template review: fitness for an agent-operated SME software suite

**Date:** 2026-11-19
**Scope:** `rust-react-template` at `4fb79b2` (ticket 0029 in progress), judged against the goal: a suite of commodity SME capabilities that is secure, safe, performant and easy to scale, works well with AI agents, takes part in agentic workflows, and is easy for agents to operate, diagnose, triage and fix.
**Business model:** Flagrante is custom SaaS. Each customer gets a single-tenant environment, run mostly by AI ops agents (a later step), with humans brought in by escalation. The aim is to keep each environment cheap, solo-founder cheap for now.

---

## 1. Verdict

The template is an unusually strong base for agents to **build and change** software. It is weak at helping agents **run, diagnose and repair** it, and at letting the app **take part in agentic workflows** beyond answering MCP calls. The engineering inside is excellent. What's around it is missing: telemetry, operator tools, outbound events, scheduling, agent identity and auditing. Those are what an ops-agent business model depends on.

## 2. What's strong (keep it)

- **Agents can work on it.** The rules are layered (`AGENTS.md`, then one per area), there's a glossary, and 40 ADRs record the options weighed. Reference modules show what to copy, and `make new-module` scaffolds a module that already compiles and has tests.
- **Rules are enforced by the build, not prose.** `check-modules`, `check-module-deps`, `check-sql-schemas`, `deny.toml` wrappers, per-crate `clippy.toml`, and `composed_app.rs` (fails on a missing `operation_id`, summary, policy or `OPERATIONS` row).
- **A factory loop:** spec → ticket → worktree and PR → two reviewers → auto-merge → learnings folded back into the docs. `make check-changed` keeps each change's checks short.
- **Every operation is an MCP tool** (ADR 0034), called in-process through the same middleware as REST, so login, authorization, validation and errors are identical.
- **Safe to retry:** an `Idempotency-Key` on every write (ADR 0032) and version checks (`If-Match`, exposed to agents as `expected_version`) on every update (ADR 0016).
- **One error shape** (ADR 0022): `code` to branch on, plus `fields` and `requestId`.
- **Correct under failure:** a transactional outbox, events ordered per record, dead letters, an injected clock, and tests against real Postgres.
- **Authorization at three levels** (ADR 0040). Lists are filtered in SQL, and a test proves the SQL filter and the in-memory check agree. Another user's row returns 404 rather than revealing it exists.
- **Events are already CloudEvents 1.0** (`crates/common/events/src/envelope.rs`), the right format to send outside the app (see 4.3).
- **Deployment:** a distroless image, and the server refuses to start in prod with the dev JWT secret (`crates/server/src/config.rs`).

Decided and out of scope here: Poem stays, the `flagrante` naming stays, and single-tenant is deliberate.

## 4. Gaps, with direction

Each gap is meant to become a spec. Priority and dependencies are in section 6.

### 4.1 SPA sign-in (P0, a blocker)

The production build doesn't work against its own API.
- Use OIDC authorization code with PKCE in the SPA against the configured identity provider (`APP_JWT_ISSUER`), and attach the token in the hey-api client config.
- Keep the dev proxy for local development.
- Add a journey or screen test that proves a production-mode build sends a token.

### 4.2 OpenTelemetry traces and metrics, and a correlated error trail (P0)

The OpenTelemetry hook at `crates/server/src/telemetry.rs:23` is empty, and there are no metrics.
- **Traces:** an OTLP exporter from `tracing-opentelemetry`; spans for each HTTP request, MCP tool call, SQL query, worker claim and handler.
- **Traces that cross async boundaries.** Add the CloudEvents distributed-tracing extension (`traceparent`) to the event envelope, so a handler's span links to the request that published the event. Without this, an agent can't follow "the request succeeded but the email never went out".
- **Metrics:** request rate, errors and latency per `operation_id`; per queue, depth, the age of the oldest job, attempts and dead letters; relay lag (outbox `seq` against dispatched); projection lag; DB pool saturation; idempotency replays; 412/409 counts (signs of contention).
- **Correlation:** put `traceId` in the `ErrorBody` alongside `requestId`, so an agent holding a failed tool result can jump straight to the trace.
- **Cost:** in solo mode, start with AWS's OTLP endpoints (X-Ray/CloudWatch) or a free-tier Grafana Cloud. The OTLP exporter keeps the backend swappable.

### 4.3 Operator surface and runbooks (P1)

Today, dead letters, lag and replays are reached only by raw SQL on `messaging.job`.
- **Add a platform `ops` module.** It's guarded (an `operator` role) and exposed over REST and MCP like everything else:
  - list and inspect dead letters, including the `last_error`, payload and trace link;
  - retry or discard a dead letter;
  - show queue depth, oldest job and lag for each subscription and projection;
  - show subscription state (registered, retired, backfill progress);
  - show compaction status;
  - give a health detail beyond the DB ping.
- **Runbooks as code.** Write one markdown runbook for each error `code`, each metric alert and each failure mode: symptom → likely cause → which `ops` tool to check → the fix. Store them in the repo and serve them as **MCP resources** so an ops agent loads the right one. Add a test that fails when an `ErrorCode` or an alert has no runbook, following the existing pattern for refusal statuses.
- **Mark ops tools' risk.** A replay or discard needs `destructiveHint` (see 4.7) and an audit record (4.4).

### 4.4 Agent identity, on-behalf-of, and an audit log (P1)

- **The standard:** OAuth 2.0 Token Exchange (RFC 8693). The token's `sub` stays the user, and an `act` claim names the actor, which can chain (agent → sub-agent). `may_act` limits who may act for whom. Service accounts (agents acting for no one) use the client-credentials grant, with the `client_id`/`azp` claim as the subject.
  - MCP's authorization spec is built on OAuth 2.1, so this fits the existing `/mcp` discovery (RFC 9728).
  - **Check which identity provider you'll use.** Token exchange support varies: Keycloak and Okta support it, and Entra has its own OBO flow. Last I knew, Cognito didn't support token exchange natively; confirm before choosing.
- **The Principal grows an actor chain.** It becomes `Principal::User { id, roles, attr, actor: Option<Actor> }`, resolved by `PrincipalResolver` from `act` and `azp`. Policies can then condition on the actor, e.g. "agents may not `delete`" or "agents may approve only under $X". That's a deny rule in the existing YAML, so no new mechanism is needed.
- **The audit log.** Make it an append-only table in a `audit` schema, written **in the same unit of work** as the change, so a change can't commit without its record. Each row holds:
  - the principal (subject and actor chain);
  - `operation_id`, the resource type and id, and its version before and after;
  - `request_id` and `trace_id`;
  - the idempotency key;
  - a timestamp.
- **Keep it apart from the outbox.** It has its own retention, with no compaction. Expose it read-only through the `ops` module, and through each resource's history where a screen needs one.
- **Add `actor` to the event envelope** as an extension attribute, so subscribers and outbound sinks know who caused an event.

### 4.5 Scheduled and deferred work (P1, new gap)

ADR 0015 removed jobs. Business workflows need "remind in 3 days", "close stale quotes nightly" and approval timeouts.
- **Keep Postgres as the source of truth for what is due.** `messaging.job` already has `run_at`, so a deferred job is a `Tx` method plus a `Handlers` registration (ADR 0015's own consequence).
- **Declare recurring schedules in code**, as topics and subscriptions are. A cron expression and a handler, registered by `migrate` into `messaging.schedule`, and turned into `job` rows by the worker ("next due").
- **What fires it:** whatever wakes the worker.
  - On containers, the current poll loop.
  - On Lambda, an **EventBridge Scheduler** rule invoking a `worker --drain` handler every minute, which runs until the queue is empty or the time budget is spent.
  - Don't create one EventBridge schedule per job. That puts state in two places, can't be tested against local Postgres, and gives ops agents two systems to check.
- **Faster wake-up (optional).** After a commit that writes to the outbox, the server can send a fire-and-forget nudge (an async Lambda invoke) so reactions don't wait up to 60 seconds. The minute tick stays as the backstop. This closes "Waking the worker other than by polling" in the not-built list.
- This rewrites ADR 0015; supersede it with a new ADR.

### 4.6 Outbound events: taking part in agentic workflows (P1)

Today MCP only works one way: agents call in, and nothing goes out.

**Two different kinds of "broadcast"; keep them apart:**
1. **Between instances** (exists: the `Bus`, Redis, ADR 0039). This is for live UI updates. It fits Lambda poorly (4.8).
2. **Out of the app** (missing). It notifies external agents, workflow engines (n8n, Zapier, Step Functions, Claude agents) and other systems.

**Recommendation: add "sinks" to the common crates.** A sink is an outbox subscription whose handler delivers outside the app, so it gets ordering per record, retries, dead letters, backfill and the operator surface for free.
- **A webhook sink.** It POSTs the CloudEvent, signed per the Standard Webhooks spec (HMAC, timestamp, id), and uses the event id as the receiver's dedup key.
- **An EventBridge sink** (`PutEvents`). On AWS this is the cheapest fan-out to Step Functions, Lambda and SQS, with no infrastructure of our own.
- **Who may register.** Registrations are data owned by a platform module, guarded by policy, and manageable over MCP. An agent can subscribe a workflow to `invoice.approved` at runtime.
- **Security (important).** Events carry each record's full state. A sink must not leak rows its owner couldn't read. Either sinks run as a principal and each event is checked against that principal's row policy before delivery, or registering a sink is admin-only and the topic's data is reviewed for exposure. Decide this in the spec.
- **MCP notifications** are tied to a session and don't survive on Lambda. Treat them as optional; webhooks and EventBridge are the durable path.

### 4.7 MCP tool hints and the prompt-injection path (P2)

- **Generate hints from the spec:** `readOnlyHint` for GET; `destructiveHint` for DELETE and for operations tagged destructive (`archive`, an ops discard); `idempotentHint` where it applies (PUT, and every write given an `Idempotency-Key`); `openWorldHint` for operations that reach external systems (mail, SMS, webhooks).
- Add a per-operation override beside `REST_ONLY` in `crates/server/src/tools.rs`, and a composed test listing each tool's hints so changes show in diffs.
- **Prompt injection:**
  - Mark user-written fields in output schemas (a `x-untrusted` schema extension). Have the server's MCP instructions tell agents that such fields are data, never instructions.
  - Keep tool *descriptions* static, from code, never interpolated from data.
  - The real defence is the authorization from 4.4: an injected agent still can't do what its principal and actor policy forbid. Make "agents can't do destructive things without a human" a default deny in policy, not a hope.

### 4.8 Lambda hosting (P2: cost)

Rust on Lambda is a good fit: fast cold starts and small memory. Poem has a Lambda adapter (`poem-lambda`). For many small single-tenant environments, **scaling to zero is the business case**: an idle customer should cost close to nothing. The parts that hold state must be redesigned first:

| Holds state today | On Lambda |
|---|---|
| The worker poll loop | `worker --drain`, run by an EventBridge Scheduler tick plus a post-commit nudge (4.5) |
| MCP sessions held in process (ADR 0034) | Sessions must survive any instance: run MCP stateless (streamable HTTP allows serving without a session), or keep sessions in Postgres |
| Redis bus plus SSE live topics (ADR 0039, ticket 0024) | Lambda can't hold subscriptions. Use API Gateway WebSockets or Lambda response streaming, or drop live push for Lambda environments and let clients poll |
| DB pool per process | A burst of Lambdas causes a connection storm. Use pool size 1–2 and RDS Proxy (a fixed cost), or a Postgres with its own pooler |
| JWKS fetched at startup | Paid on every cold start: cache it and fetch it lazily |

**Cost traps to design out up front:**
- **The database, not compute, sets the cost per tenant.** Look at Aurora Serverless v2 with auto-pause (scales to 0 ACU, but resuming takes seconds) or a serverless Postgres. Price the trade between always-on and cold resume per tenant tier.
- **A NAT gateway costs about $30+/month per AZ per environment.** A Lambda in a VPC that must reach the identity provider, SES or webhook targets needs one, unless you use VPC endpoints where they exist, a NAT instance, or keep Lambda out of the VPC with a publicly reachable DB using TLS and IAM auth.
- **Cap blast radius with reserved concurrency per tenant**, so a runaway agent can't run up an unbounded bill. Add AWS Budgets alerts per environment.

Keep the container host working. Aim for **one codebase, two hosts**, with every stateful part behind a trait and chosen by config.

### 4.9 Rate limiting and quotas (P2)

- **DDoS and per-IP limits:** handle at the edge (CloudFront + WAF rate-based rules, or Shield Standard by default). WAF costs about $5/month per web ACL plus rules, so share one at the edge across tenants rather than one per environment.
- **API Gateway in front of everything?**
  - An HTTP API is cheap and has a native JWT authorizer and stage/route throttling, but no per-client quotas.
  - A REST API has usage plans and per-key quotas, but costs about 3× as much per request.
  - A *custom* Lambda authorizer would duplicate the app's auth, adding latency and cost.
  - Use API Gateway for routing and coarse throttling, not as the auth layer.
- **The real risk in single-tenant is a runaway agent, not a DDoS.** Only the app knows the resolved principal and actor. Add a per-principal and per-actor limit in the app; it can be approximate (in memory, or a Postgres counter). Reserved concurrency (4.8) is the hard backstop.
- **Request body limits and timeouts:** neither exists in the app today. API Gateway caps payloads and has a roughly 30-second timeout, but the container host needs its own limits, so add them in `build_app`.

### 4.10 Extract `crates/common` into a versioned platform (P2)

Every `make init` clone forks the platform today, so fixes don't spread across the suite.
- **A `flagrante-platform` repo** containing a workspace of today's `common/*` crates, tagged with semver. Apps depend on it as a git dependency pinned to a tag, which is free; move to a private registry later if needed. Use Renovate to bump versions across app repos.
- **Ship the tooling, not just the crates.** The real coupling is in the scripts: `check-modules`, `check-module-deps`, `check-sql-schemas`, `new-module`, `check-changed`. Move them into a `cargo xtask` or a `flagrante` CLI binary in the platform repo, so apps get updated checks with the crates. Also ship the module template (`crates/module-template`) as data in that CLI.
- **Ship the platform's own migrations with it.** The `messaging` schema (and later `audit`, `access` and the schedule tables) must migrate as part of a platform version.
- **Share the docs too.** Platform ADRs and the platform part of the agent rules should come from the platform package, so a platform change reaches every app's agents.

### 4.11 Commodity capability ports (P2)

Add blob storage (S3), email (SES), SMS (AWS End User Messaging), and later payments and PDF generation. Each is a **port** in common with a production adapter and a hand-written Fake for tests, following `Mailer`/`FakeMailer` in `crates/reference/users`. Deliver outbound sends through the outbox, so retries and dead letters (and the operator surface) cover them. Note that SES and SMS start in sandbox mode, and getting production access takes days; start the requests early.

### 4.12 A reference module for in-app agents (P2)

A module where an agent runs *inside* the app, using the Claude API, and calls the app's own MCP tools for a signed-in user. It shows, in code worth copying:
- on-behalf-of tokens (`act` = the in-app agent);
- policies that condition on the actor;
- audit records naming the agent;
- tool hints driving a human-approval step;
- untrusted fields kept out of instructions.

It depends on 4.4 and 4.7.

### 4.13 JWKS refresh cap (P3)

Today any token with an unknown key id forces a key re-fetch, with no cap (`crates/common/web/src/auth.rs`, `Jwks::verify`). That lets anyone hammer the identity provider, and on Lambda it adds latency. Fix: limit refreshes to at most one per N seconds, and remember unknown key ids briefly.

### 4.14 Ops agents per tenant (future)

This is the product's operating model. It depends on 4.2 (traces and metrics), 4.3 (operator tools and runbooks), 4.4 (its own identity and audit), 4.5 (scheduled health checks) and 4.7 (hints that decide what needs escalation). Build the evals for it alongside (section 5): inject faults into a scratch environment, such as a poisoned event, a stuck projection or a clock skew, and grade whether the agent diagnoses and fixes it, or escalates.

## 5. Agent rules: condense, or restructure? (pushback)

**Your hypothesis:** condense the ADRs and rules into a strong `CLAUDE.md`, build a first-class codebase to copy, and drive it with evals.

**I agree with** the evals and with the codebase as the main lever. Reference code is followed more reliably than prose.

**I disagree with one condensed file.** Everything in `CLAUDE.md` is loaded on every task, so condensing still pays the whole context cost on each change. It also drops the reasons the ADRs give, which are what an agent needs for a case the rules didn't foresee. Instead:

1. **Turn rules into checks first.** Go through the rules in the backend `AGENTS.md` and mark each one "a check could enforce this" or "needs judgment". Every check-able rule becomes a script, lint or composed test, then is removed from the prose. The repo already does this well; finish the job. A check costs no context and can't be skipped.
2. **Load guidance only when needed.**
   - **A short `CLAUDE.md`, under about 150 lines.** It holds the invariants you can't check, the commands, and a map of where things are.
   - **Task skills** loaded on demand: `add-module`, `add-operation`, `add-subscriber`, `add-policy`, `add-projection`, `triage-dead-letter`. Each holds that task's rules and points at the reference code.
   - **ADRs stay as they are.** They're the reasons, read only when a rule is in question; don't put them in the default context.
3. **Keep "copy the reference".** It's your strongest doc.
4. **Evals decide.** Build a harness before restructuring, so the change is measured, not argued:
   - **Tasks:** about 10–20 canonical ones (add a module; add a field through every layer; add a subscriber; add a policy scope; fix a seeded bug; triage a seeded dead letter).
   - **Graders:** `make check` plus hidden acceptance tests plus a rubric reviewer (your existing `standards` and `spec` reviewers).
   - **Measures:** pass rate, review rounds, tokens, wall-clock time and rule violations.
   - **Variants:** today's docs, a condensed `CLAUDE.md`, and skills plus checks.
   - **Grow it from the factory.** Every factory learning is a real slip, so turn each into an eval case. A learning folded into the docs should come with the eval that proves it helps.

If the condensed single file wins the evals, ship it. I expect skills plus checks to win on tokens and match on pass rate, but that's a hypothesis too.
