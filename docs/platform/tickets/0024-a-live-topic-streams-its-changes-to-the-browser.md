# A topic a module declares live streams its changes to every browser following it, from any instance

## Description

A screen shows what it fetched and goes stale when someone else changes it. Nothing tells it to refetch: the only way out of the backend is a request. Behind a load balancer the change may commit on one instance, or arrive via the worker, while the browser's connection sits on another.

ADR 0039 brought in the bus (`app-bus`) that solves the cross-instance half, but nothing uses it yet: no module broadcasts, there is no SSE route, and the frontend has no way to follow one. So there is nothing for agents to copy.

Make it generic, as MCP is (ADR 0034): a module declares a topic **live**, and every change to that topic reaches the browsers following it. That takes no code per module beyond the declaration, and on the frontend one hook per screen. The stream carries only a doorbell (topic, key, version), never state. The browser refetches through the ordinary API, which stays the truth and does the authorization.

## Evidence (as of 2026-11-16)

- `app-bus` (`crates/common/bus/`) is in the workspace and tested over a real Valkey. `Context::with_bus`/`bus()`, `Module::broadcasts()` and `AppConfig::bus(required)` are wired in. No module calls `broadcasts()`, so no app needs Valkey yet.
- No route in `crates/` serves `text/event-stream`, and `frontend/src/` has no `EventSource` or streaming reader.
- The frontend client is generated by `@hey-api/openapi-ts` 0.64.0, which generates no SSE client. `EventSource` can't send the `Authorization: Bearer` header our one auth scheme needs (ADR 0025).
- Envelopes already carry what a doorbell needs: `key` and `version` (`app_events` `envelope.rs`), and the topic's name.

## Proposed approach

1. **Declare.** `Module::live::<T: Topic>()`: the module's topic is streamed. It implies `broadcasts()`, so the server and worker then require `APP_REDIS_URL` (ADR 0039). A topic is live only if its own module says so.
2. **Broadcast from the worker.** For each live topic, the platform, not the module, adds a subscription with queue `live.<topic name>` from `latest`, merged into `server::handlers` beside the modules' own. Its handler publishes `LiveChange { topic, key, version }` on one channel, `live_changes`, from `ctx.bus()`. A failed publish fails the delivery, so the worker retries it like any other. Ordered per key, as every queue is.
3. **Stream.** `GET /api/live?topics=<name>,<name>` as SSE.
   - It's a plain poem route beside `/health`, not in the spec, so it isn't an MCP tool and `REST_ONLY` needn't list it.
   - It needs a valid bearer token (`JwtVerifier`) and refuses any topic that isn't live (`ErrorBody`, 400).
   - One `Hub<LiveChange>` per instance with `with_listening_within(ZERO)`. Each stream filters the hub's messages to its topics.
   - Events: `connected` first, `change` per message, `gap` on `Received::Gap`, and a keep-alive comment every 15 s so proxies don't cut an idle stream.
   - It ends when the token expires, so the client reconnects with a fresh one, and when the server shuts down.
4. **Filter hook.** The stream passes each change through a `Visibility` seam (subject, change → bool) that allows everything in the template. This is where a multi-tenant app adds its rule, and the ADR says it must before it declares a topic live.
5. **Follow, frontend.** `src/lib/live.ts` holds one shared connection per tab, read with `fetch` and a streaming body parser so it sends the bearer token. It reconnects with backoff and resubscribes when the set of topics followed changes.
   - `useLive(topic, queryKeys)` invalidates the given TanStack queries on a `change` to its topic.
   - On `connected` (each connect, so each reconnect too) and on `gap`, it invalidates all of them: what was missed is refetched.
6. **Reference.** `notes` declares `.live::<NoteTopic>()`. The notes list and the edit dialog follow it, so another user's edit shows without a reload. An open edit dialog keeps what the user typed and still gets the existing `412` handling on save.
7. **Docs.** A platform ADR (the stream, the doorbell-only rule, the visibility caveat). `crates/AGENTS.md` and `frontend/AGENTS.md` rules point at `notes` as the reference. The glossary gains **Live Topic**.

## Acceptance criteria

- [ ] `Module::live::<T>()` exists, implies `broadcasts()`, and a non-live topic can't be streamed (refused with `ErrorBody`).
- [ ] A worker delivering a live topic's event publishes its `LiveChange`; a failed publish is retried (tested with `Valkey::allow_publishing(false)`).
- [ ] Journey (`crates/server/tests/journeys/`): two composed apps sharing one Valkey stand for two instances. A note edited through one reaches a stream opened on the other, once the worker delivers it.
- [ ] Journeys: a stream opened without a valid token is refused. One whose token expires ends. A reconnect is told `connected` again.
- [ ] The visibility seam filters per subscriber, tested with a rule that hides one key.
- [ ] Frontend (`src/test/`, MSW streaming the events):
  - [ ] the notes list refetches on a `change` to a note;
  - [ ] it refetches on `gap` and on reconnect;
  - [ ] it doesn't refetch for another topic;
  - [ ] an open edit dialog keeps its input.
- [ ] `make dev`: an edit in one browser shows in another without a reload.
- [ ] Platform ADR, `crates/AGENTS.md`, `frontend/AGENTS.md` and the glossary updated. `make check` passes.

## Open questions

- Whether `useLive` should invalidate only the changed key's detail query plus the lists, or every query given. The simple version (all given) is the default unless a screen proves it too chatty.
- Whether the token-expiry close should send a final `expired` event so the client refreshes its token first. It depends on how the app gets tokens, which the template leaves out (ADR 0025).

## Notes

- Not a durable feed. A missed doorbell costs a refetch, never data: the API is the truth (ADR 0039).
- Health (separate ticket): the bus becomes the first integration check, reported on `/health/status` and never failing readiness, since the bus is best effort.
