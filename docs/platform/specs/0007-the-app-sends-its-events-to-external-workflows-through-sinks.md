# The app sends its events to external workflows through sinks

## Problem

Agents can call the app over MCP (ADR 0034), but the app tells nobody outside it when something happens. So an external agent, n8n, Zapier, Step Functions or a Claude agent can't act when, say, an invoice is approved, short of polling the API.

- The `Bus` only broadcasts between the app's own instances, best effort, for live screens (ADR 0039).
- Outbox subscriptions are delivered only to handlers compiled into the worker, and only `migrate` registers them (ADR 0014, `crates/common/persistence/src/messaging.rs`).
- Events are already CloudEvents 1.0 in JSON (`crates/common/events/src/envelope.rs`, ADR 0012), so the format is settled; delivering them outside is not.

**The security problem, plainly.** Each event carries the **whole record** as it now is, not just "invoice 42 changed" (ADR 0012); the outbox keeps every record's latest event forever (ADR 0033). Inside the app, a list or a fetch shows a person only the rows their policies allow (ADR 0040). A sink skips that check: whoever registers a sink on a topic receives every change to every record of it, including records they couldn't open in the app. Registering a sink is therefore as powerful as reading the whole topic.

## Solution overview

- **A sink is an outbox subscription whose handler delivers each event outside the app.** It gets what every subscription has: order per record, retries, dead letters, backfill (ADR 0013, 0033, 0035) and, once it exists, the ops surface (Spec 0005).
- **Two kinds in v1** (question 2): a **webhook**, an HTTPS `POST` signed per [Standard Webhooks](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md), and **Amazon EventBridge**, through [`PutEvents`](https://docs.aws.amazon.com/eventbridge/latest/APIReference/API_PutEvents.html).
- **Sinks are data, registered at runtime** over REST and so MCP, by a new platform module, `sinks` (question 4).
- **Only admins register sinks, and only on topics their author has marked exportable**, so a topic is exposed whole, knowingly (question 1). Agents may not register them (question 6).

## Behaviour

### Registering

- `crates/platform/sinks`, beside `access`, kept by `make init`. Operations: `create_sink`, `list_sinks`, `get_sink`, `update_sink` (enable, disable, change URL or event types), `rotate_sink_secret`, `delete_sink`, and `send_test_event`, each with a summary written for an agent.
- A sink names one topic, optionally some of its event types (`invoices.invoice_approved`), and one destination.
- Creating, changing and deleting sinks are `sinks` actions that a **baseline rule** gives to `admin` alone, as `access`' admin actions are (ADR 0040), so no runtime grant can hand them to another role (question 1). Reading sinks is granted to `admin` by default and can be granted on.
- `topic!` gains `exportable: bool`, required, so each topic's author decides whether its data may leave the app (question 1). `create_sink` refuses a topic that isn't exportable. The reference topics are exportable.
- When actors exist (Spec 0006), a baseline DENY refuses the `sinks` write actions to any agent; until then `sinks` can't tell an agent from the admin it acts for (question 6).

### One queue per sink

- Creating a sink writes its own row to `messaging.subscription`, queue `sinks.<sink id>`, never reused, under the relay's lock as `migrate` does (ADR 0014, `crates/common/db/migrations/0001_messaging.sql`). So one failing endpoint holds up only its own records' later versions, never another sink's (question 4).
- It starts from `latest`: it receives only events published after it was created (question 3).
- A worker claims sink queues by their kind (`messaging.subscription.kind = 'sink'`), not by name, since every build has the one sink handler. ADR 0014 is amended for this.
- Deleting a sink calls `messaging.retire` (ADR 0014): pending deliveries become dead letters, visible to `ops`.
- Disabling a sink holds its jobs, undelivered, until it's enabled again.

### Delivering

- **Webhook.** `POST` of the event's CloudEvent JSON, unchanged, with `webhook-id` (the event id, the receiver's dedup key), `webhook-timestamp` and `webhook-signature` (`v1,` HMAC-SHA256 of `id.timestamp.body`), per Standard Webhooks (checked 2026-11-19).
  - The secret is `whsec_` plus 32 random bytes, generated by the app, shown once at creation and rotation. During a rotation both signatures are sent for 24 hours, as the spec allows.
  - Any `2xx` is delivered. A `410 Gone` disables the sink. A `3xx` is a failure and redirects aren't followed. A 15-second timeout.
  - Only `https://` URLs. The address is resolved and refused when private, loopback or link-local (`169.254.0.0/16`, the cloud metadata endpoint), then connected to by that address, per [OWASP's SSRF cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) (checked 2026-11-19).
- **EventBridge.** One `PutEvents` entry per event to the bus ARN the sink names: `Source` the app's name plus the CloudEvent `source`, `DetailType` its `type`, `Detail` the whole CloudEvent. A failed entry (`FailedEntryCount`) is a failed delivery. The app's IAM role needs `events:PutEvents` on that bus, which the deployment grants.
- Each record's events leave in version order, but a receiver should still compare `entityversion`: EventBridge doesn't promise order, and an operator's rerun of a dead letter delivers late (ADR 0013).
- An event too large for its destination (1 MB per `PutEvents` request) is dead-lettered with that reason.

### Retries

- A sink's job is retried for **24 hours** before it's a dead letter, about 30 attempts on the existing backoff (10 s doubling, at most an hour), instead of the outbox's 5 (`MAX_ATTEMPTS`, `crates/common/persistence/src/messaging.rs`). `messaging.job` already records `max_attempts` per job (question 5).
- Dead letters are retried or discarded through `ops` (Spec 0005).

### Docs

- `docs/platform/glossary.md` gains **Sink**; a new ADR records sinks, and ADR 0014 and 0012 (`exportable`) are amended.

## Out of scope

- Sinks acting as a principal, with each event checked against its row access, and thin events (question 1): both stay possible later.
- Other destinations: SQS, SNS, Kafka, MCP notifications (tied to a session, so not durable), CloudEvents' own webhook handshake ([spec](https://github.com/cloudevents/spec/blob/main/cloudevents/http-webhook.md), checked 2026-11-19).
- Transforming or filtering an event's fields per sink.
- Receiving events from outside.

## Open risks

- **The exposure is real.** An admin, or anyone holding an admin's token, can send a topic's whole history to any HTTPS URL. The audit log (Spec 0006) is what shows it happened.
- **Secrets are stored in the database**, so anyone who can read it can forge the app's webhooks. Encrypting them is a later step.
- **Actors** (question 6) depend on Spec 0006; whichever lands second adds the DENY.
- **Personal data leaves the app.** Erasing a person can't reach copies a receiver already holds.
- **The AWS SDK** is a large dependency for one call; `deny.toml` confines it to `sinks`, as it confines `redis` (ADR 0039).

## Needs Human Input (factory)

Prices and limits were checked on 2026-11-19 at the linked pages.

1. **Who may register a sink, and how is it kept from leaking records the registrant couldn't see?**
   - *Why it matters:* a sink receives each record whole (Problem). Whoever registers one sees the topic's every record, whatever their row access in the app.
   - *Options:*
     - **Admins only, topic exposed whole, on topics marked exportable.** One baseline rule and one `topic!` field. Safe while admins may see every row, as the reference modules' default grants give them (`crates/reference/notes/core/policies/default_grants.yaml`). Risk: a module that hides rows even from admins leaks them, unless its author leaves the topic unexportable.
     - **A sink acts as a principal; each event is checked against its row access before it's sent.** Lets any user register safely. Costs each topic a mapping from its record to its policy's attributes, and a plan per event. A record leaving the principal's view just stops arriving, so the receiver keeps a stale copy and never learns why.
     - **Thin events: ids only; the receiver fetches what it may see through the API.** Safest. But every receiver needs its own credentials and a call back, Step Functions and Zapier included, and it sees the record as it is when it calls, not as it was at the change (why ADR 0012 rejected thin events).
   - *Recommendation:* admins only, on exportable topics: cheapest, and matches the single-tenant app (ADR 0040). The other two can be added beside it later without breaking a sink.
   - *Depends on it:* "Registering", the security risk.

2. **Which destinations are in v1?**
   - *Why it matters:* webhooks reach anything with a URL (n8n, Zapier, a Claude agent's endpoint); EventBridge reaches Step Functions, Lambda and SQS with no public endpoint.
   - *Options:*
     - **Webhook only.** No AWS dependency, one adapter, and no charge per event beyond data transfer.
     - **EventBridge only; webhooks through its [API destinations](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-api-destinations.html).** One adapter. $1.00 per million events plus $0.20 per million webhook calls, each 64 KB billed as one ([pricing](https://aws.amazon.com/eventbridge/pricing/)). AWS-only, a 5-second receiver timeout, no Standard Webhooks signature (basic, OAuth or API key instead).
     - **Both.** Two adapters and the AWS SDK; EventBridge at $1.00 per million events.
   - *Recommendation:* both: webhooks are the universal path, and EventBridge is the cheapest fan-out on AWS, where environments are expected (`Review-2026-19-11.md`, 4.8).
   - *Depends on it:* "Delivering", the AWS SDK risk.

3. **Does a new sink receive history (backfill), or only new events?**
   - *Why it matters:* a workflow reacting to "invoice approved" mustn't re-run for every invoice ever approved; a receiver keeping a copy (a warehouse, a search index) needs every record first.
   - *Options:*
     - **Only new events.** The usual reaction (ADR 0033: reactions start from `latest`).
     - **Chosen per sink: new events, or every record's latest state first.** Free to build (ADR 0035 already backfills in chunks); an admin can flood a receiver, or bill EventBridge, for a whole topic.
     - **Always history.** Wrong for workflows.
   - *Recommendation:* only new events in v1; a per-sink choice can be added later, since a sink's start is fixed when it's created.
   - *Depends on it:* "One queue per sink".

4. **Are sinks registered at runtime as data, or at deploy time as configuration?**
   - *Why it matters:* today only `migrate` registers subscriptions (ADR 0014), so a runtime sink changes that rule; but "an agent wires a workflow" needs runtime.
   - *Options:*
     - **Configuration, registered by `migrate`.** No ADR change; adding a sink is a deploy, and nothing is managed over MCP.
     - **Data, a queue per sink.** Amends ADR 0014 (claims by kind); each endpoint fails alone.
     - **Data, one code-registered queue per topic whose handler sends to every sink.** No ADR change, but one endpoint down retries and holds up every sink on that topic, and redelivers to those that succeeded.
   - *Recommendation:* data, a queue per sink: runtime and isolated, for one amended rule.
   - *Depends on it:* "One queue per sink", "Registering".

5. **How long does a sink keep retrying an endpoint that's down?**
   - *Why it matters:* the outbox gives up after 5 attempts, about 2.5 minutes (ADR 0013), so a receiver's 10-minute outage dead-letters everything sent meanwhile.
   - *Options:*
     - **The outbox's 5 attempts.** No change; an operator retries in bulk afterwards (`retry_dead_letters`, Spec 0005).
     - **24 hours**, as EventBridge API destinations retry (185 times, [docs](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-api-destinations.html)). A per-sink `max_attempts`, which jobs already store.
     - **About 3 days**, [Standard Webhooks' example schedule](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md). Covers a weekend; jobs pile up longer.
   - *Recommendation:* 24 hours: rides out ordinary outages, and dead letters still surface a dead endpoint within a day.
   - *Depends on it:* "Retries".

6. **May an agent register a sink?**
   - *Why it matters:* an agent misled by text it read (prompt injection), acting for an admin, could send a whole topic to an attacker's URL in one call.
   - *Options:*
     - **Yes, as any admin action over MCP** (ADR 0034). Most useful; the exfiltration risk above.
     - **No: a DENY for agents** once Spec 0006 tells them apart. One rule; agents still read sinks and send test events.
     - **Yes, but an agent's sink starts disabled until a person enables it.** Keeps agents useful; a disabled-until-confirmed state and a screen.
   - *Recommendation:* no, for now: one rule closes the worst path; the confirmation flow can follow if agents need it.
   - *Depends on it:* "Registering", the actors risk.
